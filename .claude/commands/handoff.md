## Как устроена память проекта

Весь контекст проекта живёт в четырёх файлах. У каждого — одна роль.
Читай их **в этом порядке**:

| # | Файл | Отвечает на вопрос | Как меняется |
|---|------|--------------------|--------------|
| 1 | [project-brief.md](./project-brief.md) | **Что** это за проект и **зачем** | Редко (меняется суть проекта) |
| 2 | [state.md](./state.md) | **Где мы сейчас** и **что делать дальше** | Постоянно — это «живой снимок» |
| 3 | [changelog.md](./changelog.md) | **Что уже сделали** (по датам) | Только дописывается вниз |
| 4 | [decisions.md](./decisions.md) | **Почему** так, а не иначе | Только дописывается вниз |

Плюс [../CLAUDE.md](../CLAUDE.md) — инструкции по стеку, деплою и правилам работы.

**Правило, которое держит всё это в актуальном состоянии:**
после каждого осмысленного шага мы обновляем `state.md` + дописываем
`changelog.md` и **коммитим в git**. Поэтому история проекта = история
коммитов, а текущее положение дел всегда в `state.md`. Подробнее — в
разделе «ЖУРНАЛ ПРОЕКТА И КОММИТЫ» в `CLAUDE.md`.

## Быстрый старт для входящей нейронки

1. Прочитай 4 файла выше по порядку.
2. Глянь последние коммиты — это лента того, что реально делалось:
   ```bash
   git log --oneline -20
   ```
3. Если нужно увидеть, что менялось в конкретном шаге:
   ```bash
   git show <hash>
   ```
4. Запусти проект, убедись что он живой:
   ```bash
   npm install && npm run check
   ```
5. Возьми первый пункт из раздела «Следующие шаги» в `state.md` — и продолжай.

**Известный, сознательно отложенный минус (не блокирует, лёгкий фикс на
будущее):** `hermes_web/run.py`'s `configure_logging()` отключает
`propagate` у логгера `aiohttp.access`, чтобы не задваивать access-строки
— но на живом сервере подтверждено, что это **полностью глушит
access-лог** в journald, а не просто убирает дубли. Исправление: убрать
строку `logging.getLogger("aiohttp.access").propagate = False` в
`run.py` — по мнению ревьюера, встроенная проверка
`aiohttp.web.run_app` (`hasHandlers()`) и так не даст задвоить строки.

Живая приёмка пользователя нашла и сразу закрыла: (1) максимальная
ширина панели редактора расширена до `max(560px, 50% ширины рабочей

**Главные подводные камни:**
- `/workspace/...` внутри Docker-песочницы агента — алиас, который
  понимает только shell (`terminal`/`execute_code`); инструменты
  `write_file`/`read_file` — не-докеризованные и всегда отклонят
  абсолютный `/workspace/...` путь. Это вендорный код Hermes
  (`agent/file_safety.py`), чинится только промптом (system-сообщение в
  `quickchat.py`), не гарантированно — модель может всё равно ошибиться.
  **Это же ограничение — первопричина всей истории D-013/D-014**: промпт
  можно усилить, но нельзя гарантировать, особенно против устоявшегося
  прецедента в истории того же диалога. D-014 явно принял это как
  системный предел и вместо дальнейшего усиления промпта (A3, сознательно
  НЕ сделан) добавил надёжный ручной фолбэк (A2 — кнопка «переместить»)
  и диагностику (A1 — логирование).
- `approvals.mode: manual` (D-004) не имеет для веб-чата штатной
  подсказки про `/approve` — открытый вопрос, см. `docs/state.md`
  «Открытые вопросы / блокеры».
- Диагностика живых багов эффективнее всего через прямой запрос к
  Hermes API (`GET http://127.0.0.1:8642/api/sessions/{id}/messages` на
  сервере с `Authorization: Bearer $API_SERVER_KEY` из `~/.hermes/.env`)
  — сырая история сессии, а не только `journalctl`. Именно так была
  найдена первопричина проблемы, закрытой в D-014.
- Тестовый venv для `hermes-web`/`project_index` живёт вне репозитория,
  в scratchpad-директории конкретной сессии
  (`/tmp/claude-1000/.../scratchpad/hermes-web-venv`) — если сессия
  сброшена, создать заново по образцу плана 2026-07-26 (aiohttp/argon2-
  cffi/pytest/pytest-asyncio, версии — см. тот план).
- На сервере `hermes-web` — НЕ git-чекаут, а просто набор файлов,
  разложенных `rsync`'ом (`/home/hermes/hermes-web`). Деплой = `rsync`
  каждого изменённого файла + `systemctl --user restart
  hermes-web.service`, не `git pull`. Одноразовые тестовые аккаунты
  (`qa_temp`) создаются вручную через `hermes_web.storage.create_user` +
  `auth.hash_password` (см. `hermes_web/seed_users.py`, но его CLI требует
  интерактивный `getpass` — проще инлайновым Python-вызовом по SSH) и
  обязательно удаляются после проверки, вместе с тестовым проектом в
  `~/workspace/qa_temp`. **Уточнение (2026-08-02):** `hermes-web` не
  имеет своего venv — рабочий интерпретатор для инлайновых Python-вызовов
  на сервере это `~/.hermes/hermes-agent/venv/bin/python3.11`
  (тот же venv, что у самого агента; `seed_users.py`'ю докстринг про
  `venv/bin/python3` внутри `~/hermes-web` устарел/неверен — такой
  директории там нет).
- **Живая отладка на данных реального пользователя — только после
  бэкапа** (найдено 2026-08-02, см. запись Группы D в changelog). Перед
  любой прямой записью в файл живого проекта в рамках диагностики —
  сначала `cp`/сохранить содержимое, даже если кажется, что операция
  «безопасна» или легко обратима. Если бэкапа не оказалось, а инцидент
  всё же случился — сырая история сессии Hermes (`GET
  /api/sessions/{id}/messages`) часто содержит и предыдущее содержимое
  файла (через `read_file`/`write_file`/`edit_file` tool-сообщения), и
  unified-diff’ы правок — этим можно восстановить файл байт-в-байт, как
  было сделано в этом инциденте.
