## Как устроена память проекта

Весь контекст проекта живёт в четырёх файлах. У каждого — одна роль.
Читай их **в этом порядке**:

| # | Файл | Отвечает на вопрос | Как меняется |
|---|------|--------------------|--------------|
| 1 | [project-brief.md](./project-brief.md) | **Что** это за проект и **зачем** | Редко (меняется суть проекта) |
| 2 | [state.md](./state.md) | **Где мы сейчас** и **что делать дальше** | Постоянно — это «живой снимок» |
| 3 | [changelog.md](./changelog.md) | **Что уже сделали** (по датам) | Только дописывается вниз |
| 4 | [decisions.md](./decisions.md) | **Почему** так, а не иначе | Только дописывается вниз |

Плюс [../CLAUDE.md](../CLAUDE.md) — инструкции по стеку, деплою и правилам работы.

**Правило, которое держит всё это в актуальном состоянии:**
после каждого осмысленного шага мы обновляем `state.md` + дописываем
`changelog.md` и **коммитим в git**. Поэтому история проекта = история
коммитов, а текущее положение дел всегда в `state.md`. Подробнее — в
разделе «ЖУРНАЛ ПРОЕКТА И КОММИТЫ» в `CLAUDE.md`.

## Быстрый старт для входящей нейронки

1. Прочитай 4 файла выше по порядку.
2. Глянь последние коммиты — это лента того, что реально делалось:
   ```bash
   git log --oneline -20
   ```
3. Если нужно увидеть, что менялось в конкретном шаге:
   ```bash
   git show <hash>
   ```
4. Запусти проект, убедись что он живой:
   ```bash
   npm install && npm run check
   ```
5. Возьми первый пункт из раздела «Следующие шаги» в `state.md` — и продолжай.

**Что в процессе / недоделано:** **следующий шаг — реализация 4 багов из

`source/outer/result` — не виден/не скачивается в UI. У каждого — точная
причина и конкретный фикс уже расписаны в спеке, TDD-план ещё не
написан. После этого — под-проект C (админ-панель, метрики

**Главные подводные камни:**
- `/workspace/...` внутри Docker-песочницы агента — алиас, который
  понимает только shell (`terminal`/`execute_code`); инструменты
  `write_file`/`read_file` — не-докеризованные и всегда отклонят
  абсолютный `/workspace/...` путь. Это вендорный код Hermes
  (`agent/file_safety.py`), чинится только промптом (system-сообщение в
  `quickchat.py`), не гарантированно — модель может всё равно ошибиться.
- `approvals.mode: manual` (D-004) не имеет для веб-чата штатной
  подсказки про `/approve` — открытый вопрос, см. `docs/state.md`
  «Открытые вопросы / блокеры».
- Диагностика живых багов эффективнее всего через прямой запрос к
  Hermes API (`GET http://127.0.0.1:8642/api/sessions/{id}/messages` на
  сервере с `Authorization: Bearer $API_SERVER_KEY` из `~/.hermes/.env`)
  — сырая история сессии, а не только `journalctl`.
- Тестовый venv для `hermes-web`/`project_index` живёт вне репозитория,
  в scratchpad-директории конкретной сессии
