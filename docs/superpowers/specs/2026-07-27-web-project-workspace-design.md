## Зачем

Макет `/result/project-workspace.html` — кликабельный прототип с
захардкоженными демо-данными. Нужно подключить его к реальному
бэкенду: открыть любой существующий проект (созданный когда-то через
«Быстрый чат», перенесённый `project_move`, или мигрированный вручную,
как `physics-tasks`), продолжить с ним диалог, посмотреть и
организовать файлы, увидеть, что агент делает в реальном времени.

Отдельно всплыл реальный сценарий заказчика: несколько источников
(учебники разных авторов) с задачами, у которых **совпадают номера**
(1.1, 1.2, 1.3 — из разных книг). Плоская структура `source/outer/
result` с датой-префиксом на имени файла (как зафиксировано в
`hermes-prj-structure.md`) для этого не годится — нужны подпапки внутри
`source`/`outer`/`result` (например, по фамилии автора), чтобы разборы
с одинаковыми номерами не путались и не перезаписывали друг друга. Это
меняет ранее согласованный дизайн — см. «Изменение конвенции» ниже.

## Проверено в текущем коде и контракте Hermes API (важно)

- `chat_sessions` (`hermes-web.db`) сейчас создаётся только «Быстрым
  чатом» вместе с новым проектом в `ALL` (`quickchat.create_quick_chat`).
  Прямого способа получить/создать `chat_session` для уже существующего
  проекта — нет.
- `POST /api/chat/{chat_session_id}/send` и
  `GET /api/chat/{chat_session_id}/messages` уже не завязаны на «Быстрый
  чат» специфично — это генеральные обёртки над `quickchat.send_message`/
  `get_history`, которые принимают любой `chat_session_id`, если он есть
  в БД и принадлежит текущему пользователю. Переиспользуем как есть.
- Контракт SSE Hermes API (см. план среза 1+2, Task 4/5): `event: <name>`
  включает не только `assistant.delta`/`assistant.completed`/`done`, но и
  `run.started`/`message.started`/`tool.started`/`tool.progress`/
  `tool.completed`/`tool.failed`/`run.completed`. `handle_send_message` в
  `app.py` уже пересылает **все** именованные события в браузер как есть
  (`event: {name}\ndata: {data}`) — для «Активности агента» в этом срезе
  не нужно ничего менять в бэкенде, только научить фронтенд их
  отрисовывать.
- `GET /api/sessions/{id}/messages` отдаёт `{"role", "content",
  "timestamp", ...}` — **без** информации о том, какие tool-вызовы или
  файлы породили конкретный ответ, и без стабильного message id, на
  который можно было бы сослаться. Индекс сообщения в полученном
  массиве — единственный практичный «id» для фронтенда (как уже сделано
  в макете, `id="msg-N"`).
- `resolve_project_path(user, project_path, workspace_root)` в
  `project_index/core.py` — уже проверенный (в прошлом ревью найден и
  закрыт path-traversal баг в `move_project`) хелпер: резолвит
  `os.path.realpath` и проверяет, что путь не выходит за пределы
  `<workspace_root>/<user>/`. Переиспользуем его как первый слой защиты
  для всех новых файловых эндпоинтов, поверх добавляем второй слой —
  проверку, что путь конкретного файла не выходит за пределы
  **проекта**.
- `move_project` уже обновляет `chat_sessions.project_path`
  (`storage.update_chat_session_project_path`), а `quickchat.
  send_message` берёт `system_message` (с упоминанием `project_path`) из
  БД заново при каждой отправке — значит открытый вопрос из
  `hermes-prj-structure.md` («активную сессию после переноса придётся
  перезапускать») уже закрыт существующим кодом, доп. работы не нужно.

## Изменение конвенции: подпапки в `source`/`outer`/`result`

`hermes-prj-structure.md` фиксировал плоскую структуру («файлы прямо в
`source`/`outer`/`result`, с датой-префиксом на имени файла для
хронологии»). Реальный сценарий заказчика (несколько учебников с
одинаковой нумерацией задач) требует подпапок для разделения тем внутри
одного проекта. Меняем:

- Внутри `source`/`outer`/`result` разрешены подпапки любой вложенности
  (например `source/Иванов/`, `source/Иванов/глава1/`).
- Дата-префикс на **имени файла** сохраняется как правило (хронология
  внутри конкретной папки не теряется), но перестаёт быть единственным
  механизмом разделения — подпапки решают проблему одинаковых номеров
  между разными источниками.
- Создавать подпапки может человек через `project-workspace.html` (этот
  срез) или агент обычными файловыми инструментами по просьбе в чате
  (агент и так имеет полный доступ к дереву проекта — это не требует
  изменений в Hermes-плагине или `SOUL.md`/`AGENTS.md`, кроме
  упоминания, что подпапки — нормальная практика, не только `ALL`-стиль
  плоских файлов).
- Это решение фиксируется отдельно как `decisions.md` D-010 (см. ниже) —
  меняет уже согласованный документ, не только добавляет новую фичу.

## Архитектура

Без нового стека — тот же `hermes-web` (Python/aiohttp). Новый модуль
`hermes_web/workspace.py`, по образцу `projects.py`: обёртки над
`project_index.core` + новая файловая логика, которой в самом плагине
`project_index` нет и не должно быть (она специфична для веб-морды, не
нужна агенту — у агента и так есть прямой доступ к файловой системе
своей песочницы).

### Резолюция путей — два слоя

`workspace.py` вводит `_resolve_file_path(user, project_path,
relative_path, config)`:
1. Резолвит `project_root = project_index_core.resolve_project_path(
   user, project_path, workspace_root)` (существующий хелпер, первый
   слой — проект принадлежит пользователю).
2. `candidate = os.path.realpath(os.path.join(project_root,
   relative_path))`; проверяет `candidate == project_root` (для `path=
   ""`, не должно случаться) или `candidate.startswith(project_root +
   os.sep)` — второй слой, файл не выходит за пределы **этого**
   проекта. Иначе — `WorkspaceError` → 400.
3. Дополнительно для операций записи (`mkdir`/`upload`/сохранение файла,
   кроме трёх корневых `about.md`/`AGENTS.md`/`history.md`) — путь
   обязан лежать внутри `project_root/source/`, `project_root/outer/`
   или `project_root/result/` (`candidate` начинается с одной из трёх
   этих директорий) — иначе `WorkspaceError` → 400. Это не пускает,
   например, `POST /api/projects/mkdir` создать папку прямо в корне
   проекта поверх служебных файлов.

### Сессия чата для существующего проекта — ленивая

`quickchat.py` получает `get_or_open_session(db_conn, http_session,
config, user, project_path)`:
- Резолвит и проверяет проект (`project_index_core.get_project_detail`
  — кидает `ProjectIndexError`, если `about.md` не найден, значит это
  не проект).
- `storage.get_chat_session_for_project(db_conn, user, resolved_path)`
  — новый геттер (`SELECT ... WHERE user = ? AND project_path = ?
  ORDER BY created_at DESC LIMIT 1`, без уникального constraint'а на
  уровне схемы — двух живых пользователей достаточно, чтобы не городить
  миграцию существующей таблицы ради гонки, которой на практике не
  будет).
- Если строка есть — возвращает её как есть (переиспользуем существующую
  Hermes-сессию, диалог продолжается).
- Если нет — создаёт новую Hermes-сессию (`hermes_client.create_session`,
  тот же паттерн, что в `create_quick_chat`, но **без** создания
  `about.md`-заглушки — проект уже существует) и строку в
  `chat_sessions`.
- Используется новым эндпоинтом `POST /api/projects/open`; `create_quick_
  chat` не трогаем — у него свой сценарий (создание нового проекта в
  `ALL`), просто оба теперь используют общий низкоуровневый хелпер
  создания Hermes-сессии (мелкий рефакторинг внутри `quickchat.py`, без
  изменения его публичного контракта).

## API (`hermes-web`, все эндпоинты — под активной веб-сессией)

- **`POST /api/projects/open {path}`** → `{chat_session_id,
  project_path}`. 404, если путь не резолвится в проект пользователя
  (`ProjectIndexError`).
- **`GET /api/projects/tree?path=...`** → рекурсивный список:
  ```json
  {
    "root_files": [{"name": "about.md", "size": 512, "mtime": "..."}],
    "source": [{"relative_path": "source/Иванов/2026-07-27_a.pdf", "size": ..., "mtime": "..."}],
    "outer": [...],
    "result": [...]
  }
  ```
  `root_files` — только реально существующие из `about.md`/`AGENTS.md`/
  `history.md` (не все три гарантированы, особенно для проектов
  времён до этого среза). Папки внутри `source`/`outer`/`result`
  восстанавливаются на фронтенде из `relative_path` (совпадает с тем,
  как уже устроено дерево в макете — рендер по префиксу пути, без
  отдельного списка «папок»).
- **`GET /api/projects/file?path=<project_path>&file=<relative>`** →
  сырое содержимое (текст — inline, для редактора; `&download=1` —
  `Content-Disposition: attachment` с оригинальным именем файла).
  Доступно для чтения любого файла внутри проекта (корневые
  `about.md`/`AGENTS.md`/`history.md` + всё под `source`/`outer`/
  `result`) — на чтение ограничение на «только source/outer/result»
  не накладываем, только на запись (см. выше).
- **`POST /api/projects/file {path, file, content}`** → сохраняет
  текст. Разрешены только `.md`/`.txt` (проверка по расширению, 400 на
  остальные — не даём текстовому редактору испортить бинарник). Если
  `file == "about.md"` (ровно корневой) — сразу после записи
  `project_index_core.index_update` в `run_in_executor` (тот же паттерн,
  что уже в `quickchat.create_quick_chat`, — эмбеддинг может дойти до
  реального HTTP-вызова, нельзя блокировать event loop).
- **`POST /api/projects/mkdir {path, parent, name}`** → создаёт папку.
  `parent` — относительный путь, обязан резолвиться внутри `source`/
  `outer`/`result` (второй слой проверки выше). Коллизия имени — 409,
  без тихого авто-суффикса (та же политика, что уже принята для
  `move_project`: человек решает сам, а не получает случайное
  `-2` в имени).
- **`POST /api/projects/upload`** (`multipart/form-data`: `path`
  (проект), `target_dir` (например `source/Иванов`), `file`) →
  сохраняет с датой-префиксом на имени файла внутри `target_dir`
  (`project_index_core._add_date_prefix`, уже есть, переиспользуем),
  возвращает `{relative_path, size}`. Коллизия имени — 409, та же
  политика без авто-суффикса.
- Чат — без изменений: `POST /api/chat/{chat_session_id}/send`,
  `GET /api/chat/{chat_session_id}/messages`.

## Формат вложений в сообщении

Hermes API не принимает файлы отдельным полем в `/chat/stream` — только
`message`/`system_message` (текст). Вложения кодируются как хвост
текста сообщения, отправляемого агенту:

```
<текст пользователя>

📎 source/Иванов/2026-07-27_a.pdf, source/Иванов/2026-07-27_b.pdf
```

Фронтенд парсит этот хвост (`/\n\n📎 (.+)$/`) и при формировании
`attach-row` для только что отправленного сообщения, и при рендере
истории из `GET /api/chat/{id}/messages` (единственный источник правды
— сам текст сообщения, который агент и так видит; никакой новой таблицы
под вложения не заводим). Для `source`-файлов это даёт **точный** прыжок
«файл → сообщение» (см. «Вкладка Файлы» ниже).

## Активность агента

Без изменений на бэкенде — фронтенд подписывается на уже идущий SSE
`POST /api/chat/{id}/send` и рендерит `tool.started`/`tool.progress`/
`tool.completed`/`tool.failed`/`run.*` в панель «Активность агента» в
реальном времени. Эфемерно: при перезагрузке страницы или повторном
заходе в проект лог пуст до следующего сообщения (сознательный выбор —
Hermes API сам не хранит эти события, отдельная таблица под них ради
истории, которую и так не видно нигде, кроме этой панели, не
оправдана).

## Вкладка «Файлы»

Строится из `GET /api/projects/tree` (все файлы с категорией
`source`/`outer`/`result`, размером, mtime) плюс сопоставление с
сообщениями чата:
- **`source`** — точный `message_index` через парсинг хвоста `📎` из
  истории (см. выше).
- **`outer`/`result`** — точной привязки нет (Hermes API не отдаёт
  «какой tool-вызов создал какие файлы»), поэтому — ближайшее по
  времени сообщение агента: `mtime` файла сравнивается с `timestamp`
  сообщений из истории, берётся ближайшее **последующее**
  `assistant`-сообщение (файл появился до того, как агент отчитался о
  результате).

## Фронтенд (`project-workspace.html`)

Берём кликабельный макет почти как есть (как и `project-selector.html`
в прошлом срезе), меняется:
- Дерево — из статичного плоского списка под лейблом группы в
  рекурсивный рендер с вложенными папками (сворачивание/разворачивание),
  построенный из `GET /api/projects/tree`.
- Кнопка «новая папка» в дереве (в каждой из `source`/`outer`/`result`
  и в уже существующих подпапках) → маленький промпт с именем → `POST
  /api/projects/mkdir`.
- Кнопка загрузки (📎 в composer) → нативный file picker; перед
  фактической отправкой сообщения выбранные файлы уходят через `POST
  /api/projects/upload` в **выбранную** пользователем подпапку
  (простой `<select>`/breadcrumb-пикер по уже существующим папкам плюс
  «в корень source/outer» по умолчанию — без опции создать новую папку
  прямо из диалога загрузки, для этого есть отдельная кнопка «новая
  папка» в дереве), затем в текст сообщения добавляется хвост `📎 ...`
  с полученными `relative_path`.
- Клик по `.md`/`.txt` в дереве → тот же оверлей-редактор, что в
  макете, только читает/пишет через `GET`/`POST /api/projects/file`.
- Клик по не-`.md`/`.txt` файлу (картинки, DXF, html-результаты и
  т.п.) → скачивание через `GET /api/projects/file?...&download=1`
  (макет уже это ожидает для attach-chips/file-row, просто вместо
  `downloadPlaceholder` — реальный переход по URL).
- Открытие экрана — по клику «Открыть проект →» из
  `project-selector.html` (был плейсхолдером в прошлом срезе): `POST
  /api/projects/open` → получить `chat_session_id` → подгрузить историю
  (`GET /api/chat/{id}/messages`) → отрендерить чат, дерево (`GET
  /api/projects/tree`).
- Панель «Активность агента» подписывается на именованные SSE-события
  из уже идущего `send`-запроса (расширение уже написанного в срезе 1+2
  JS-парсера SSE, не новый код с нуля).

## Обработка ошибок

- Истёкшая/невалидная кука — 401 → редирект на `/login`, как везде
  (`requireAuth`/`apiFetch` без изменений).
- `POST /api/projects/open` на путь вне пространства пользователя или
  без `about.md` — 404.
- Hermes недоступен при ленивом создании сессии в `get_or_open_session`
  — ошибка наверх, `chat_sessions`-строка не создаётся (тот же паттерн,
  что уже есть в `create_quick_chat`, — сначала сетевой шаг, потом
  локальные операции, без «осиротевших» строк).
- `mkdir`/`upload` на коллизию имени — 409 с понятным текстом.
- `mkdir`/`upload`/сохранение файла на путь вне `source`/`outer`/
  `result` (для mkdir/upload) или вне проекта (для всех) — 400 с текстом
  ошибки, не более детально (не палим внутреннюю структуру).
- Сохранение файла не `.md`/`.txt` через редактор — 400.
- Загрузка файла с именем, содержащим `..`/`/` в самом имени файла (не
  в `target_dir`) — отклоняется на уровне `_add_date_prefix`/валидации
  имени, та же логика, что защищает `target_dir`.

## Тестирование

- `hermes_web/workspace.py`: юнит-тесты на `_resolve_file_path` (успех,
  traversal через `..` на обоих слоях, чужой пользователь), `tree`
  (пустой проект, проект без `AGENTS.md`/`history.md`, вложенные папки),
  `file` GET/POST (текст, не-md/txt → 400, реиндексация вызывается
  только для корневого `about.md`, не для `source/about.md`), `mkdir`
  (успех, коллизия → 409, попытка создать в корне проекта → 400),
  `upload` (успех с датой-префиксом, коллизия → 409, `target_dir` вне
  `source/outer/result` → 400).
- `quickchat.get_or_open_session`: новая Hermes-сессия при первом
  заходе, переиспользование существующей при повторном, `ProjectIndexError`
  на несуществующий проект, отсутствие «осиротевшей» строки при падении
  Hermes.
- `storage.get_chat_session_for_project`: несколько сессий разных
  пользователей на разные проекты не путаются.
- Явные тесты на межпользовательский доступ на каждый новый эндпоинт
  (`tree`/`file`/`mkdir`/`upload`/`open` — путь другого пользователя →
  404/400, не утечка) — тот же класс проблемы, что уже находили и
  закрывали в `move_project` в прошлом срезе, повторять эту ошибку
  нельзя.
- После деплоя — ручной приёмочный тест на `hermes.blackboxbegin.space`:
  открыть уже существующий (`physics-tasks`) и созданный «Быстрым
  чатом» проекты, продолжить диалог и убедиться что видна прежняя
  история, создать подпапку в `source`, загрузить в неё файл, отправить
  сообщение с этим вложением и увидеть, что агент реально его видит
  (например, просит `vision_analyze` на картинку), посмотреть «Активность
  агента» вживую во время ответа, отредактировать и сохранить `about.md`
  и убедиться что переиндексация прошла (например, через RAG-поиск в
  `project-selector.html`), перезагрузить страницу и убедиться что дерево
  и история сохранились, а активность — очистилась (ожидаемо).
