# Спек: удаление файлов из проекта + уникальные имена вставленных скриншотов

Дата: 2026-08-02
Статус: approved

## Контекст

Две мелкие фичи, отдельные друг от друга, но обе — доводка рабочего экрана
проекта (`project-workspace.html` + `hermes_web/workspace.py`):

1. Сейчас в дереве проекта можно только перемещать файлы/папки
   (`move_entry`), удалить — нельзя вообще.
2. Вставка скриншота из буфера обмена в поле ввода сохраняет файл под
   именем, которое браузер всегда даёт вставленному изображению
   (`image.png`). Сервер добавляет только дату (`_add_date_prefix`), так
   что вторая вставка в тот же день падает `WorkspaceCollisionError`
   ("уже существует") — коллизия тут не сигнал о реальном конфликте
   (пользователь ничего не называл сам), а артефакт схемы именования.

## Feature 1 — удаление файлов и папок

### Бэкенд (`hermes_web/workspace.py`)

Новая функция `delete_entry(user, project_path, relative_path, config) -> dict`,
по образцу существующей `move_entry`:

- Путь резолвится через уже существующий `resolve_file_path` (тот же
  path-traversal guard, что у чтения/записи/перемещения).
- Разрешено удалять: что угодно внутри `source`/`outer`/`result`
  (через `_require_within_bucket`, как в `make_dir`/`move_entry`), **или**
  что угодно в "остальном" (misc — корень проекта вне бакетов), но по тем
  же правилам, что уже показывает `_list_misc`: не скрытые (`.`-префикс)
  файлы/папки на любом уровне вложенности.
- Запрещено удалять:
  - сам корень проекта (`candidate == project_root`);
  - `about.md` / `AGENTS.md` / `history.md` (`ROOT_EDITABLE_FILES`);
  - сами папки-бакеты `source`/`outer`/`result` целиком (как у `move_entry`).
- Файл — `os.remove`, папка — `shutil.rmtree` (рекурсивно). Без корзины,
  без возможности восстановить — насовсем, подтверждение только в UI
  (см. ниже). В отличие от удаления всего проекта
  (`project_index_core.delete_project`, которое перемещает в корзину) —
  сознательно другой уровень: удаление отдельного файла происходит часто
  и точечно, трэш-папка внутри проекта добавила бы сложности (где лежит,
  кто и когда чистит, как не показывать её в дереве/misc) непропорционально
  риску.
- **Symlink guard:** если запрошенный `relative_path` сам является
  симлинком, `resolve_file_path` отдаёт `candidate` как realpath — то
  есть уже резолвленный путь ЦЕЛИ, а не самой ссылки. Удаление такого
  `candidate` стёрло бы файл/папку, на которую ссылка указывает, а не
  саму ссылку — неожиданно и опасно (в этом же модуле уже есть
  прецедент такой предосторожности: `O_NOFOLLOW` в `save_upload`).
  `delete_entry` отдельно проверяет `os.path.islink()` на нерезолвленном
  пути (`os.path.join(project_root, relative_path)`) и в этом случае
  удаляет именно ссылку (`os.remove` по нерезолвленному пути), не трогая
  цель.
- Ошибки: `WorkspaceError` (400) для всех перечисленных запретов и
  "не найден"; отдельного `WorkspaceCollisionError` тут не бывает
  (удаление не конфликтует само с собой).

### API (`hermes_web/app.py`)

`POST /api/projects/delete-entry`, тело `{path, relative_path}` —
1-в-1 паттерн `handle_project_move_entry`: `_require_user`,
`WorkspaceError` → 400, `ProjectIndexError` → 404. Регистрация рядом с
`/api/projects/move-entry`.

### Фронтенд (`project-workspace.html`)

Рядом с существующей кнопкой «→» (переместить, `move-btn`) у каждого узла
дерева (и файла, и папки, во всех секциях — `source`/`outer`/`result`/misc)
добавляется кнопка «🗑» (`delete-btn`, `data-delete="<relative_path>"`).
Обработчик:

1. `confirm()` — текст зависит от того, файл это или папка (для папки —
   явное упоминание "со всем содержимым").
2. `POST /api/projects/delete-entry`.
3. При 401 — редирект на логин, как у остальных операций.
4. При ошибке — `alert()` с текстом из `body.error`, как у `moveEntry`.
5. При успехе — если удалённый файл был открыт в редакторе
   (`currentEditorFile === relpath`), закрыть редактор
   (`closeEditorPane()`, сброс `currentEditorFile`/`editorDirty`) —
   иначе пользователь может сохранить в уже удалённый файл.
6. `refreshTreeAndFiles()`.

Корневые файлы (`about.md`/`AGENTS.md`/`history.md`, строки 530-532)
кнопки удаления не получают — они и так защищены на бэкенде, но
показывать заведомо нерабочую кнопку незачем (та же логика, по которой у
них сегодня нет кнопки "→").

## Feature 2 — уникальные имена вставленных скриншотов

Правится только клиентский обработчик `paste` на `composeInput`
(`project-workspace.html`, строки 965-970). Сервер (`save_upload`,
`_add_date_prefix`) не меняется — обычная загрузка через кнопку-скрепку
(файлы с осмысленными именами вроде `report.pdf`) по-прежнему падает
явной ошибкой при коллизии, это осознанное поведение отдельно от этой
фичи.

Перед вызовом `uploadPending`, каждому файлу из `clipboardData.items»
присваивается новое имя (через `new File([blob], newName, {type: blob.type})`,
т.к. `File.name` неизменяем после создания):

```
screenshot_ЧЧ-ММ-СС[-N].<ext>
```

- `ЧЧ-ММ-СС` — время вставки на клиенте (дату дописывает сервер через
  `_add_date_prefix`, дублировать не нужно).
- `-N` — порядковый номер внутри одного `paste`-события (начиная с 1),
  добавляется только когда изображений в событии больше одного; при
  единственном изображении суффикса нет (`screenshot_14-33-05.png`).
- `<ext>` — из MIME-типа файла (`image/png` → `png`, `image/jpeg` → `jpg`,
  `image/webp` → `webp`, иначе фолбэк `png`).

Коллизия двух отдельных `paste`-событий в одну и ту же секунду
теоретически возможна, но не устраняется намеренно (YAGNI) — сценарий
не тот, что описан в баг-репорте (повторные вставки с разницей в минуты,
несколько скриншотов в одном сообщении), и вероятность на практике
исчезающе мала.

## Вне рамок

- Массовое удаление (мультивыбор) — не запрашивалось.
- Корзина/восстановление для удалённых файлов — сознательно отклонено
  (см. Feature 1).
- Изменение схемы именования для обычной загрузки файлов — сознательно
  отклонено (см. Feature 2).
