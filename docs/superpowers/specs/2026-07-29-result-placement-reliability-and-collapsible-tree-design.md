# Спек: почему модель всё ещё не кладёт файлы в result/ + сворачиваемые папки в дереве

**Дата:** 2026-07-29 · **Статус:** черновик по итогам расследования,
**ждёт ревью пользователя** (написан без интерактивного брейнсторминга —
пользователь попросил изучить вопрос и подготовить спеку, пока отходит;
решения ниже — рекомендация, не согласованы построчно)

## Контекст

В тот же день, что был выкачен D-013 (селектор «папка для результата» +
усиленное системное сообщение), живой прогон в том же проекте
(`dem/fizika-kinematika/physics-tasks`, разбор Кирика 3.27) показал: баг
не исчез. Модель не спросила, куда класть файл, и не положила в
`result/`. Пользователь прислал скриншот и попросил разобраться.

Два отдельных запроса в одном сообщении — расследование первого и
дизайн второго ниже разделены на две независимые части.

## Часть A: почему усиленная инструкция не сработала

### Расследование (прямые данные с сервера, не теория)

1. Файл действительно лежит там, где не должен:
   `resolved_path: /workspace/dem/fizika-kinematika/physics-tasks/3-kirik-3-23-29/solution_3_27.html`
   — это корень проекта, не `result/`. Проверено прямым запросом к
   Hermes API (`GET /api/sessions/{id}/messages` на сервере,
   `hermes_session_id = web_7dc4e63efa3942429b8e1d1e06b0171a`).
2. `result/` в этом проекте существует и в нём уже лежит `result/kirik`
   (пустая подпапка, созданная пользователем через UI — как раз то, что
   чинили в D-013). Модель её не тронула вообще.
3. Ключевая находка — история сообщений этой сессии показывает, что
   модель писала в `3-kirik-3-23-29/` **и раньше, много раз, начиная с
   2026-07-28**, и в этом же проекте лежат десятки файлов вида `1.1.html`
   … `1.12.html` прямо в корне проекта с датой `Jul 24` — то есть за
   **пять дней до того**, как в проекте вообще появился `source/outer/result`
   (тот интерфейс выкачен 2026-07-27, см. `changelog.md`). Модель просто
   продолжает свою же устоявшуюся, давно закреплённую в истории разговора
   схему — писать в пронумерованные папки прямо в корне проекта — а не
   игнорирует инструкцию из чистого непослушания.
4. Смотрели вызов `write_file` для сообщения о задаче 3.27
   (`message id 738`, `timestamp 2026-07-29T12:16:02`) — модель указала
   абсолютный путь `.../3-kirik-3-23-29/solution_3_27.html` **сразу**, без
   колебаний и без вопроса пользователю — то есть с точки зрения модели
   это не было неуверенным выбором, для которого сработала бы фраза
   «спроси пользователя, если не уверен». Модель была уверена — просто
   не в том, в чём нужно.
5. Деплой на сервере (обе части D-013 — `project-workspace.html` и
   `quickchat.py` с фиксом нестрокового `result_target`) прошёл раньше
   этого разговора (11:08 и 11:47 UTC против разговора в 12:16-12:17 UTC)
   — код на сервере был актуальным. Но нет способа подтвердить постфактум,
   **действительно ли фронтенд этой открытой вкладки отправил
   `result_target` в этом конкретном запросе** — `hermes-web` не логирует
   ни входящее тело запроса, ни собранное системное сообщение, только
   сама история диалога видна через Hermes API. Это слепая зона
   диагностики, не только этого случая.

### Вывод

Промпт-инструкция — даже усиленная, с конкретным путём — конкурирует не
с "невнимательностью" модели, а с **месяцами устоявшегося прецедента в
истории того же самого продолжительного диалога**. Одного абзаца в
системном сообщении одного хода недостаточно, чтобы перевесить десятки
предыдущих успешных примеров в контексте той же сессии. Это системное
ограничение чисто промпт-based решения, а не баг реализации D-013 —
сама механика (нельзя технически заблокировать запись модели, см. D-013)
никуда не делась.

### Предлагаемое решение (3 части, можно внедрять по отдельности)

**A1. Логирование `result_target`/факта усиления на каждый ход (низкий
риск, чисто диагностика).** Без этого невозможно доказательно
диагностировать похожие случаи в будущем — сейчас можно только гадать,
дошло ли усиление до модели. Логировать (не полное системное сообщение
целиком, чтобы не раздувать логи и не писать пользовательский текст
без необходимости) — `chat_session_id`, `result_target` (или его
отсутствие), был ли абзац добавлен (прошла ли валидация).

**A2. Human-in-the-loop подстраховка: кнопка «→ переместить в result/»
на файлах/папках вне source/outer/result (раздел «остальное»).**
Раз модель нельзя гарантированно заставить слушаться промпта — даём
пользователю дешёвый, надёжный способ поправить результат руками одним
кликом, вместо ручного `mv`/переписывания пути в чате. Переиспользует
уже существующий паттерн защиты пути (`resolve_file_path` +
`_require_within_bucket`, как в `move_project`/`save_upload` — см.
`docs/decisions.md`, срез 3). Кнопка появляется у каждой записи в
секции «🗂 остальное» дерева файлов, спрашивает целевую подпапку внутри
`result/` (переиспользовать уже существующий `resultTargetSelect` —
дефолт то же значение), делает `move`/`rename` на сервере.

**A3. Усилить формулировку системного сообщения ещё раз — дешёвая правка,
не панацея.** Учитывая находку 4 выше (модель не была не уверена, а была
уверена не в том), одной эмоциональной интенсивности в тексте («ОБЯЗАТЕЛЬНО»,
повтор в начале и в конце сообщения) вряд ли хватит против устоявшегося
прецедента — включаю в спеку как самый дешёвый из трёх шагов, но не
единственный.

**Открытый вопрос пользователю:** делать ли все три части сразу, или
только A1+A2 (диагностика + надёжный ручной фолбэк, не полагаясь на
переубеждение модели)? Рекомендация: A1+A2 обязательно, A3 — опционально
(дёшево, но эффект недоказуем).

## Часть B: сворачиваемые вложенные папки в дереве файлов

### Мотивация

Тот же живой пример — `misc`/«остальное» в этом проекте уже содержит
дюжины файлов и две вложенные папки (`3-kirik-3-20`, `3-kirik-3-23-29`),
и это будет только расти (та же причина, что в Части A — модель кладёт
файлы вне буketov). Дерево сейчас рендерит всё раскрытым целиком, без
возможности свернуть — на долгих проектах список станет неудобным для
навигации.

### Текущая реализация (для контекста)

`renderFolderNode(node, bucketClass, depth)`
(`static/project-workspace.html:442-458`) рекурсивно рендерит HTML для
каждой папки и файла без какого-либо состояния свёрнутости — просто
плоский обход дерева с отступами по `depth`.

### Решение

- Каждая папка (`.node.folder-*`, не файл) получает кликабельный
  треугольник-индикатор (`▶`/`▼`) слева от иконки `📁` — клик по
  треугольнику или по всей строке папки (кроме кнопки `＋`) переключает
  свёрнутость.
- Состояние свёрнутости — `Set` путей (`collapsedPaths`, тот же паттерн,
  что уже применялся для `manuallyCreatedFolders`/выбора
  `resultTargetSelect` — но здесь, в отличие от выбора целевой папки,
  предлагается **сразу** делать персистентным через `localStorage` по
  ключу проекта, а не только в памяти вкладки: не наступать второй раз
  на тот же класс "теряется при перезагрузке", который уже дважды был
  причиной жалоб в этом проекте).
- Дефолт — **всё развёрнуто**, как сейчас (не менять привычное поведение
  без явного действия пользователя) — сворачивание запоминается только
  после того, как пользователь сам свернул хотя бы одну папку.
- `renderFolderNode` при рендере пропускает рекурсивный вызов для детей
  и файлов свёрнутой папки, но саму строку папки рисует всегда (чтобы
  можно было развернуть обратно) — плюс к иконке добавляется счётчик
  количества скрытых файлов/папок внутри (например `(12)`), чтобы
  свёрнутая папка не выглядела пустой.
- Применяется одинаково во всех секциях — `source`/`outer`/`result`/
  `misc` — один и тот же механизм, без специального поведения на bucket.

**Открытый вопрос пользователю:** сворачивать по умолчанию папки с
большим числом файлов (например, `misc`, если в ней больше N записей)
сразу при первом открытии, а не только по клику? Рекомендация: нет —
проще и предсказуемее всегда стартовать развёрнутым, тем более что
Часть A может со временем вообще опустошить `misc`, если A2 приживётся.

## Что не делаем (в обеих частях)

- Не патчим и не пытаемся обойти вендорный код Hermes (`file_safety.py`)
  — то же ограничение, что в D-013.
- Не делаем автоматический перенос файлов из `misc` в `result/` без
  подтверждения пользователя (A2 — это кнопка, требующая клика, не
  фоновая задача) — риск переместить то, что пользователь специально
  хотел оставить на месте (например `3-kirik-3-20`, у которого явно
  устоявшийся смысл в этом же проекте).
- Не меняем поведение выбора `resultTargetSelect` (D-013) — эта спека
  добавляет вокруг него диагностику и ручной фолбэк, не переделывает его.

## Тесты (черновой набросок, уточнить в плане)

- A1: юнит-тест, что `quickchat.send_message`/`_system_message_for`
  логирует (через стандартный `logging`, не печатает в stdout) факт
  наличия/валидности `result_target` для хода.
- A2: `workspace.py` — новая функция `move_to_bucket`/аналог, тесты на
  path-traversal (тот же набор проверок, что уже есть для
  `save_upload`/`make_dir`), коллизию имени, успешный перенос.
- B: чисто фронтенд, без автотестов (как и в D-013) — ручная проверка:
  свернуть папку → файлы скрыты, счётчик показывает верное число →
  перезагрузка страницы → свёрнутость сохранилась → развернуть обратно.
