# Спек: почему модель всё ещё не кладёт файлы в result/ + сворачиваемые папки в дереве

**Дата:** 2026-07-29 · **Статус:** согласован с пользователем, готов к
написанию плана реализации (Часть A: A1+A2, без A3; Часть B: свёрнуто по
умолчанию при открытии проекта; плюс Часть C, добавленная по итогам
обсуждения)

## Контекст

В тот же день, что был выкачен D-013 (селектор «папка для результата» +
усиленное системное сообщение), живой прогон в том же проекте
(`dem/fizika-kinematika/physics-tasks`, разбор Кирика 3.27) показал: баг
не исчез. Модель не спросила, куда класть файл, и не положила в
`result/`. Пользователь прислал скриншот и попросил разобраться.

Два отдельных запроса в одном сообщении — расследование первого и
дизайн второго ниже разделены на две независимые части.

## Часть A: почему усиленная инструкция не сработала

### Расследование (прямые данные с сервера, не теория)

1. Файл действительно лежит там, где не должен:
   `resolved_path: /workspace/dem/fizika-kinematika/physics-tasks/3-kirik-3-23-29/solution_3_27.html`
   — это корень проекта, не `result/`. Проверено прямым запросом к
   Hermes API (`GET /api/sessions/{id}/messages` на сервере,
   `hermes_session_id = web_7dc4e63efa3942429b8e1d1e06b0171a`).
2. `result/` в этом проекте существует и в нём уже лежит `result/kirik`
   (пустая подпапка, созданная пользователем через UI — как раз то, что
   чинили в D-013). Модель её не тронула вообще.
3. Ключевая находка — история сообщений этой сессии показывает, что
   модель писала в `3-kirik-3-23-29/` **и раньше, много раз, начиная с
   2026-07-28**, и в этом же проекте лежат десятки файлов вида `1.1.html`
   … `1.12.html` прямо в корне проекта с датой `Jul 24` — то есть за
   **пять дней до того**, как в проекте вообще появился `source/outer/result`
   (тот интерфейс выкачен 2026-07-27, см. `changelog.md`). Модель просто
   продолжает свою же устоявшуюся, давно закреплённую в истории разговора
   схему — писать в пронумерованные папки прямо в корне проекта — а не
   игнорирует инструкцию из чистого непослушания.
4. Смотрели вызов `write_file` для сообщения о задаче 3.27
   (`message id 738`, `timestamp 2026-07-29T12:16:02`) — модель указала
   абсолютный путь `.../3-kirik-3-23-29/solution_3_27.html` **сразу**, без
   колебаний и без вопроса пользователю — то есть с точки зрения модели
   это не было неуверенным выбором, для которого сработала бы фраза
   «спроси пользователя, если не уверен». Модель была уверена — просто
   не в том, в чём нужно.
5. Деплой на сервере (обе части D-013 — `project-workspace.html` и
   `quickchat.py` с фиксом нестрокового `result_target`) прошёл раньше
   этого разговора (11:08 и 11:47 UTC против разговора в 12:16-12:17 UTC)
   — код на сервере был актуальным. Но нет способа подтвердить постфактум,
   **действительно ли фронтенд этой открытой вкладки отправил
   `result_target` в этом конкретном запросе** — `hermes-web` не логирует
   ни входящее тело запроса, ни собранное системное сообщение, только
   сама история диалога видна через Hermes API. Это слепая зона
   диагностики, не только этого случая.

### Вывод

Промпт-инструкция — даже усиленная, с конкретным путём — конкурирует не
с "невнимательностью" модели, а с **месяцами устоявшегося прецедента в
истории того же самого продолжительного диалога**. Одного абзаца в
системном сообщении одного хода недостаточно, чтобы перевесить десятки
предыдущих успешных примеров в контексте той же сессии. Это системное
ограничение чисто промпт-based решения, а не баг реализации D-013 —
сама механика (нельзя технически заблокировать запись модели, см. D-013)
никуда не делась.

### Предлагаемое решение (делаем A1+A2, A3 — нет, см. решение ниже)

**A1. Логирование `result_target`/факта усиления на каждый ход (низкий
риск, чисто диагностика).** Без этого невозможно доказательно
диагностировать похожие случаи в будущем — сейчас можно только гадать,
дошло ли усиление до модели. Логировать (не полное системное сообщение
целиком, чтобы не раздувать логи и не писать пользовательский текст
без необходимости) — `chat_session_id`, `result_target` (или его
отсутствие), был ли абзац добавлен (прошла ли валидация).

**A2. Human-in-the-loop подстраховка: общее действие «переместить/
переименовать» на любом файле/папке дерева, в любом бакете.** Раз модель
нельзя гарантированно заставить слушаться промпта — даём пользователю
дешёвый, надёжный способ поправить результат руками одним кликом, вместо
ручного `mv`/переписывания пути в чате. Переиспользует уже существующий
паттерн защиты пути (`resolve_file_path` — как в `move_project`/
`save_upload`, см. `docs/decisions.md`, срез 3; но не `_require_within_bucket`
для места назначения — раз конечная папка может быть и в `misc`, см. Часть C
про такое же ослабление для `save_file`). Кнопка
«→ переместить» появляется у каждой записи дерева — файла и папки, в
`source`/`outer`/`result`/`misc` одинаково, — не только в «остальном»:
пользователь явно попросил, что если решит перестроить структуру внутри
проекта, он должен без проблем смочь пересобрать содержимое, а не только
вытаскивать файлы из `misc`. Диалог спрашивает целевой путь (переиспользовать
уже существующий `resultTargetSelect`-паттерн выбора папки, плюс поле для
нового имени, если нужно переименовать), делает `move`/`rename` на
сервере.

**A3. Усилить формулировку системного сообщения ещё раз — дешёвая правка,
не панацея.** Учитывая находку 4 выше (модель не была не уверена, а была
уверена не в том), одной эмоциональной интенсивности в тексте («ОБЯЗАТЕЛЬНО»,
повтор в начале и в конце сообщения) вряд ли хватит против устоявшегося
прецедента — не делаем в этом срезе (см. решение ниже).

**Решение (принято пользователем 2026-07-29):** делаем A1 + A2. A3 — не
делаем: раз промпт-инструкция всё равно не гарантирует результат (см.
находку 4), дальнейшая правка формулировки не стоит усилий по сравнению с
надёжным ручным фолбэком A2.

**A2, уточнение объёма (по итогам решения пользователя):** это не узкая
кнопка «→ result/» на файлах вне буketov, а **общее действие
«переместить/переименовать»**, доступное на любом файле и любой папке в
дереве, в любом бакете (`source`/`outer`/`result`/`misc`) — не только
чтобы вытащить файл из `misc`, но и чтобы пользователь мог в любой момент
перестроить структуру проекта по-своему (например, если решит завести
новые подпапки в `result/` и разложить туда старые файлы). Один и тот же
UI-элемент и один и тот же backend-эндпоинт закрывают обе задачи —
специального узкого действия «в result» отдельно от общего move не
делаем, это было бы дублированием.

## Часть B: сворачиваемые вложенные папки в дереве файлов

### Мотивация

Тот же живой пример — `misc`/«остальное» в этом проекте уже содержит
дюжины файлов и две вложенные папки (`3-kirik-3-20`, `3-kirik-3-23-29`),
и это будет только расти (та же причина, что в Части A — модель кладёт
файлы вне буketov). Дерево сейчас рендерит всё раскрытым целиком, без
возможности свернуть — на долгих проектах список станет неудобным для
навигации.

### Текущая реализация (для контекста)

`renderFolderNode(node, bucketClass, depth)`
(`static/project-workspace.html:442-458`) рекурсивно рендерит HTML для
каждой папки и файла без какого-либо состояния свёрнутости — просто
плоский обход дерева с отступами по `depth`.

### Решение

- Каждая папка (`.node.folder-*`, не файл) получает кликабельный
  треугольник-индикатор (`▶`/`▼`) слева от иконки `📁` — клик по
  треугольнику или по всей строке папки (кроме кнопки `＋`) переключает
  свёрнутость.
- Состояние свёрнутости — `Set` путей (`collapsedPaths`, тот же паттерн,
  что уже применялся для `manuallyCreatedFolders`/выбора
  `resultTargetSelect` — но здесь, в отличие от выбора целевой папки,
  предлагается **сразу** делать персистентным через `localStorage` по
  ключу проекта, а не только в памяти вкладки: не наступать второй раз
  на тот же класс "теряется при перезагрузке", который уже дважды был
  причиной жалоб в этом проекте).
- Дефолт — **всё свёрнуто** при каждом открытии проекта (см. «Решение»
  ниже — это меняет черновой вариант «всё развёрнуто», обсуждённый до
  согласования с пользователем).
- `renderFolderNode` при рендере пропускает рекурсивный вызов для детей
  и файлов свёрнутой папки, но саму строку папки рисует всегда (чтобы
  можно было развернуть обратно) — плюс к иконке добавляется счётчик
  количества скрытых файлов/папок внутри (например `(12)`), чтобы
  свёрнутая папка не выглядела пустой.
- Применяется одинаково во всех секциях — `source`/`outer`/`result`/
  `misc` — один и тот же механизм, без специального поведения на bucket.

**Решение (принято пользователем 2026-07-29):** по умолчанию, при каждом
открытии проекта, все папки дерева стартуют **свёрнутыми** (не только
`misc` — одинаково во всех секциях, без специального поведения на
bucket, как и было задумано). Это меняет дефолт из черновика: там
предполагалось «всё развёрнуто, пока пользователь сам не свернёт» — по
факту пользователь предпочитает противоположное. `localStorage`-состояние
по-прежнему хранит **отклонения от дефолта** (какие папки пользователь
явно развернул), а не факт «пользователь хоть раз сворачивал» — то есть
при следующем открытии проекта разложенные вручную папки остаются
развёрнутыми, а остальные — свёрнутыми.

## Часть C: файлы вне буketov (misc) нельзя читать/редактировать — только скачать

### Находка

При разборе Части A всплыл смежный баг: клик по файлу `.md`/`.txt` в
дереве открывает читалку/редактор (`openEditor`, см.
`static/project-workspace.html:552-560`) для `source`/`outer`/`result`,
но для `misc` — тот же обработчик клика (`static/project-workspace.html:486`)
явно форсирует скачивание независимо от расширения:

```js
n.addEventListener('click', () => {
  const relpath = n.dataset.relpath;
  if (n.classList.contains('folder-misc')) { downloadFile(relpath); return; }
  if (/\.(md|txt)$/i.test(relpath)) openEditor(relpath);
  else downloadFile(relpath);
});
```

Пользователь как раз и жаловался на это — а файлы, которые не попадают в
`source/outer/result`, это ровно те, что задевает баг из Части A, так что
пользователь с высокой вероятностью натыкался на этот же частный случай.

### Решение

Убрать специальный ранний `return` для `misc` — вместо него применять ту
же проверку расширения, что и для остальных buckets: `.md`/`.txt` в
`misc` тоже открываются в `openEditor`, всё остальное (включая бинарные
файлы) по-прежнему скачивается. Никакого отдельного пути для `misc` не
остаётся — один и тот же обработчик клика для всех бакетов:

```js
n.addEventListener('click', () => {
  const relpath = n.dataset.relpath;
  if (/\.(md|txt)$/i.test(relpath)) openEditor(relpath);
  else downloadFile(relpath);
});
```

**Уточнение по итогам проверки backend (это не только фронтенд-фикс):**
чтение (`GET /api/projects/file` → `workspace.read_file`,
`hermes_web/workspace.py:195`) уже работает для любого пути внутри
проекта — `read_file` не вызывает `_require_within_bucket`, только
проверку "внутри проекта" из `resolve_file_path`. Но сохранение
(`POST /api/projects/file` → `workspace.save_file`,
`hermes_web/workspace.py:204-212`) **явно блокирует** любой путь вне
`source/outer/result`/`ROOT_EDITABLE_FILES` — вызывает
`_require_within_bucket`, которая для `misc`-пути поднимет
`WorkspaceError("путь должен быть внутри source/outer/result")`. Значит
одной фронтенд-правки недостаточно: открыть на чтение `misc`-файл
получится, а нажатие «сохранить» упадёт с ошибкой. Нужно также убрать
вызов `_require_within_bucket` из `save_file` (оставить только проверку
расширения `EDITABLE_EXTENSIONS` и проверку "внутри проекта" из
`resolve_file_path`, которая уже защищает от path-traversal) — тем самым
`save_file` становится симметричен `read_file` по объёму разрешённых
путей, а `misc` окончательно становится полноценным разделом дерева, а
не только для чтения.

## Часть D (на будущее, не в этом срезе): скилы/команды в рамках проекта

Пользователь упомянул желание в будущем создавать и редактировать
скилы/команды в рамках проектов — пока не уточнено, о чём именно речь
(собственные скилы/tools для агента Hermes внутри конкретного проекта,
или что-то в духе `.claude/commands`/`.claude/skills` для самого
репозитория `hermes-web`, привязанное к проекту). Пользователь пока сам
не уверен в объёме — зафиксировано здесь как направление на будущее, не
как часть текущего плана. Требует отдельного брейнсторминга с
уточняющими вопросами, когда пользователь будет готов сузить объём.

## Что не делаем (в обеих частях)

- Не патчим и не пытаемся обойти вендорный код Hermes (`file_safety.py`)
  — то же ограничение, что в D-013.
- Не делаем автоматический перенос файлов между бакетами без
  подтверждения пользователя (A2 — это кнопка, требующая клика на
  конкретном файле/папке и подтверждения целевого пути, не фоновая
  задача и не массовая операция) — риск переместить то, что пользователь
  специально хотел оставить на месте (например `3-kirik-3-20`, у
  которого явно устоявшийся смысл в этом же проекте).
- Не меняем поведение выбора `resultTargetSelect` (D-013) — эта спека
  добавляет вокруг него диагностику и ручной фолбэк, не переделывает его.

## Тесты (черновой набросок, уточнить в плане)

- A1: юнит-тест, что `quickchat.send_message`/`_system_message_for`
  логирует (через стандартный `logging`, не печатает в stdout) факт
  наличия/валидности `result_target` для хода.
- A2: `workspace.py` — новая функция move/rename (например `move_entry`,
  точное имя — в плане), работающая для файла и для папки, из любого
  bucket в любой bucket (включая `misc`). Тесты на path-traversal (тот
  же набор проверок, что уже есть для `save_upload`/`make_dir`),
  коллизию имени на целевом пути, успешный перенос файла, успешный
  перенос непустой папки целиком.
- B: чисто фронтенд, без автотестов (как и в D-013) — ручная проверка:
  открыть проект → все папки свёрнуты по умолчанию → развернуть одну →
  перезагрузка страницы → именно она осталась развёрнутой, остальные
  по-прежнему свёрнуты.
- C: юнит-тест `workspace.save_file` — сохранение по пути вне
  `source/outer/result` (аналог `misc`) больше не поднимает
  `WorkspaceError`, содержимое реально записано; плюс регрессионный тест,
  что path-traversal (`../`) по-прежнему отклоняется (через
  `resolve_file_path`, а не через убранный `_require_within_bucket`) —
  граница защиты сдвигается, но не исчезает. Клик по `.md`/`.txt` в
  `misc` → `openEditor` вместо `downloadFile` — ручная проверка, как и
  остальной UI дерева (D-013 прецедент).
