## Зачем

Согласованный дизайн веб-интерфейса (`decisions.md` D-009, 5 экранов,
кликабельные HTML-макеты в `/result/`) фиксирует требования к бэкенду,
которого пока не существует. Этот срез реализует минимум, достаточный
чтобы человек открыл `hermes.blackboxbegin.space` в браузере, вошёл под
своим логином и начал разговор с Hermes — без Matrix/Element, без VPN.
Макет `home.html` (уже согласован) явно фиксирует: плитка «Быстрый чат» —
это не изолированный чат в вакууме, а создание проекта в `ALL`
(`попадёт в ALL, разберётесь с темой позже»`) — то есть этот срез с
первого дня интегрируется с уже готовым плагином `project_index`
(под-проект A), а не откладывает это на срез 3.

## Проверено на реальном сервере (важно)

Перед спеком подключились к VPS (`hermes@212.115.55.116` и `root@…`) и
сверили архитектурные предположения с фактическим состоянием — не
гадать, а прочитать реальный код и конфиг (правило `CLAUDE.md`):

- **У Hermes уже есть готовый HTTP API для программного управления
  чатом** — `gateway/platforms/api_server.py` (OpenAI-совместимый +
  собственные `/api/sessions/*`). Не нужно изобретать способ «говорить с
  Hermes из браузера» — Hermes это уже умеет:
  - `POST /api/sessions` — создать сессию (свой `session_id`).
  - `POST /api/sessions/{id}/chat` / `POST /api/sessions/{id}/chat/stream`
    — сообщение в сессию, второй вариант — SSE-стрим токенов.
  - `GET /api/sessions/{id}/messages` — история сообщений (для
    возврата в чат после перезагрузки страницы).
  - Аутентификация — bearer-токен `API_SERVER_KEY`, `connect()` вообще
    отказывается стартовать API-сервер без него.
  - По умолчанию слушает **только `127.0.0.1:8642`** (`DEFAULT_HOST =
    "127.0.0.1"`, `DEFAULT_PORT = 8642`) — наружу не торчит, симметрично
    уже работающему `hermes-dashboard` на `9119`.
- **Платформа `api_server` сейчас выключена.** В `~/.hermes/config.yaml`
  и `~/.hermes/.env` нет ни одного упоминания `api_server`/`API_SERVER_*`
  — включается она чисто по факту наличия `API_SERVER_KEY` в `.env`
  (`connect()` требует ключ), без записи в `config.yaml` — та же модель,
  что уже используется для Matrix (`MATRIX_HOMESERVER`/`MATRIX_ACCESS_TOKEN`
  живут только в `.env`, `config.yaml` их не знает).
- **Рабочая директория гейтвея — процесс-wide, не per-сессия.**
  `TERMINAL_CWD` (см. `gateway/run.py`) — одна настройка на весь
  гейтвей-процесс, включая API-сервер. У `AIAgent()`, который создаётся
  внутри `_run_agent` в `api_server.py`, нет параметра `cwd`/
  `working_directory` на сессию. **Следствие:** нельзя переключать
  рабочую директорию агента по HTTP-сессии на уровне ОС — изоляция
  проекта достигается **конвенцией в system-промпте** (см. «Каждое
  сообщение» ниже), тем же способом, каким уже работает подпапка на
  задачу из `SOUL.md`.
- **Публичный домен уже поднят и указывает на нужный VPS.**
  `hermes.blackboxbegin.space` → `212.115.55.116` (проверено `dig`,
  совпадает с IP из `docs/state.md`). На VPS сейчас **нет** ни Caddy, ни
  nginx, ни apache — `ss -tlnp` пусто на портах 80/443/8642, `ufw
  inactive`. Значит установка реверс-прокси и минимального firewall —
  часть этого среза, а не отдельная задача «когда-нибудь».
- **Локальный `/etc/caddy` на машине-администраторе — другая машина**,
  обслуживает не связанные с этим проектом сайты (`ap-simple-test` и
  т.п.). Конфиг Caddy для Hermes пишется с нуля на VPS `212.115.55.116`,
  никак не переиспользует локальный.

## Архитектура

```
Интернет → Caddy (hermes.blackboxbegin.space, авто-TLS Let's Encrypt)
              → hermes-web (наш бэкенд, 127.0.0.1:8643, systemd user-юнит под hermes)
                   ├─ отдаёт статику: login.html/home.html (+JS/CSS) из /result, доработанные под fetch()
                   ├─ SQLite (hermes-web.db): users, web_sessions, chat_sessions
                   ├─ импортирует hermes-plugins/project_index/core.py напрямую
                   │     (создание проекта в ALL, about.md, index_update — без похода через LLM)
                   └─ проксирует чат → Hermes API server (127.0.0.1:8642, тот же VPS)
                           платформа api_server — включается через API_SERVER_KEY в .env
```

Новый компонент в этом репозитории — `hermes-web/` (Python/aiohttp),
рядом с `hermes-plugins/`, по тому же принципу: чистый импортируемый
пакет, минимум зависимости от внутренностей Hermes сверх уже
задокументированного контракта API-сервера.

**Почему Python/aiohttp, а не второй язык.** Один язык на весь стек:
`project_index` уже на Python, сам Hermes — Python/asyncio с тем же
`aiohttp`, что и его API-сервер. Фронтенд — без сборки: те же
кликбельные макеты `login.html`/`home.html` из `/result/`, дополненные
обычным `fetch()`/`EventSource`, никакого React/бандлера/второго рантайма
на VPS.

**Рассмотренная и отклонённая альтернатива.** Направить готовый
OpenAI-совместимый фронтенд (Open WebUI и т.п. — сам Hermes упоминает их
в докстринге `api_server.py` как совместимые) прямо на API-сервер,
поверх — только Caddy и базовая авторизация. Резко меньше кода, но
перечёркивает уже согласованный дизайн D-009 («Созвездие», логин без
списка пользователей, чат сразу создаёт проект в `ALL` с
`about.md`) — получился бы универсальный чат-UI, а не то, что
согласовывали с заказчиком. Отклонено.

## Модель данных (SQLite, `hermes-web.db`)

- **`users`** — `username` (`dem`/`rost`), `password_hash` (argon2),
  `role` (`owner`/`participant`), `display_name`. Без самостоятельной
  регистрации — см. «Сиды пользователей» ниже.
- **`web_sessions`** — куки-сессии входа в веб-интерфейс: `token`
  (случайный, не JWT), `username`, `created_at`, `expires_at`. Не
  путать с `chat_sessions`/Hermes-сессиями — это разные уровни (вход в
  веб-морду vs конкретный разговор с агентом).
- **`chat_sessions`** — `id`, `user`, `project_path` (workspace-
  relative), `hermes_session_id`, `created_at`, `last_message_at`.
  По одному «быстрому чату» пользователь может открыть сколько угодно
  раз (каждый клик — новый проект в `ALL`); список для будущего
  «Работа с проектами» (срез 3) читается из этой же таблицы плюс из
  индекса `project_index`.

## Аутентификация

- **Логин.** Форма `login.html` (уже согласована, без списка
  пользователей — намеренное решение по безопасности из D-009) →
  `POST /login {username, password}`. Бэкенд сверяет argon2-хэш, при
  успехе ставит сессионную куку (httponly, secure, samesite=strict,
  случайный токен, TTL в `web_sessions`).
- **Логаут.** `POST /logout` — удаляет строку `web_sessions`, кука
  становится недействительной немедленно (не JWT — мгновенный отзыв
  важнее statless-масштабирования при двух пользователях).
- **Сиды пользователей.** Без UI в этом срезе — разовый ручной скрипт
  `hermes-web/seed_users.py`, запускается на сервере вручную, создаёт
  `dem` (owner) и `rost` (participant) с паролями, которые задаёт
  заказчик при запуске. Полноценное управление пользователями —
  `admin.html`, отдельный срез 4, здесь не строим.
- **Rate limit.** Простой лимит на `/login` (например, 5 попыток / 5
  минут на IP+username) — эндпоинт публичный на реальном домене, а не
  спрятан за SSH-туннелем, как нынешний дашборд.
- **Роль в ответе.** `home.html` уже условно прячет плитку
  «Администрирование» по `data-role-only="owner"` — бэкенд отдаёт роль
  в начальном HTML/сессии; JS-переключатель ролей, который сейчас в
  макете для демо-показа, убирается.

## «Быстрый чат»: создание проекта и общение с Hermes

**Старт разговора** (`POST /api/quick-chat`, требует активную веб-сессию):
1. Бэкенд генерирует слаг `ГГГГ-ММ-ДД_chat-<короткий id>`, создаёт
   `workspace/<user>/ALL/<слаг>/` на диске.
2. Пишет туда placeholder `about.md` (статус `active`, «Название
   проекта» = «Новый разговор ЧЧ:ММ», «Краткое описание» = «Ждёт первого
   сообщения») — обязательные поля заполнены, чтобы `parse_about_md` не
   упал.
3. Вызывает `project_index.core.index_update(user, project_path)`
   напрямую (импорт модуля, не через LLM) — проект сразу виден в
   индексе, пусть пока без содержательного embedding.
4. Создаёт Hermes-сессию: `POST /api/sessions` на `127.0.0.1:8642`
   (свой `session_id`, например `web_<uuid>`), сохраняет строку в
   `chat_sessions` (user, project_path, hermes_session_id).
5. Отдаёт браузеру `{project_path, session_id}` → фронт переходит в чат.

**Каждое сообщение:**
1. Браузер → `POST /api/chat/{session_id}/send {text}` на наш бэкенд.
2. Бэкенд проксирует в Hermes: `POST
   /api/sessions/{hermes_session_id}/chat/stream`, добавляя
   `ephemeral_system_prompt` с указанием текущего `project_path` — агент
   пишет файлы туда, а не в корень `workspace` (то же соглашение о
   подпапках на задачу, что уже в `SOUL.md`).
3. SSE от Hermes прокидывается 1:1 в SSE к браузеру, без буферизации —
   фронт дорисовывает ответ по мере поступления токенов.
4. Обновление `about.md`/пересчёт индекса делает **сам агент**, по уже
   задеплоенному правилу в `SOUL.md` («после правки about.md — вызови
   `project_index_update`») — бэкенду дополнительно ничего делать не
   нужно.

**Возврат в чат** (обновление страницы / следующий день): `GET
/api/sessions/{hermes_session_id}/messages` — история забирается из
Hermes и рендерится как есть, разговор продолжается той же сессией.

## Обработка ошибок

- **Hermes API server недоступен** (гейтвей перезапускается/упал) →
  `POST /api/chat/{id}/send` возвращает понятную ошибку клиенту
  («Hermes временно недоступен, попробуйте через минуту»); сообщение
  пользователя не теряется, фронт предлагает «повторить».
- **wormsoft.ru недоступен при создании проекта** → не блокирует
  (уже решено в `project_index`: `index_update` без embedding,
  доиндексируется агентом позже).
- **Неверный логин/пароль** → одно и то же сообщение «неверный логин
  или пароль» независимо от того, что именно неверно — не палим
  существование логина (та же логика, что уже заложена в дизайне
  `login.html`).
- **Истёкшая/невалидная кука сессии** → редирект на `/login`, без
  деталей причины в ответе.
- **Гонка при создании папки проекта** (два клика «Быстрый чат»
  подряд) → слаг включает случайный суффикс, коллизия практически
  невозможна; если всё же случится — `core.py` уже кидает
  `ProjectIndexError`, отдаём как 500 с логированием, пользователь
  просто жмёт кнопку ещё раз.

## Деплой и инфраструктура

**На VPS, от `root` (разово):**
- Установить Caddy (apt), включить как systemd-сервис.
- `Caddyfile`:
  ```
  hermes.blackboxbegin.space {
      reverse_proxy 127.0.0.1:8643
  }
  ```
  Caddy сам получает и продлевает Let's Encrypt-сертификат.
- Включить `ufw` (сейчас неактивен) с минимальным набором: `22/tcp`
  (SSH), `80/tcp` + `443/tcp` (Caddy) — раз это первый публичный порт,
  который открывается на этом VPS, явно ограничиваем остальное, а не
  полагаемся на то, что «больше ничего не слушает».

**Под `hermes` (без sudo, как и всё остальное):**
- В `~/.hermes/.env` добавить `API_SERVER_KEY` (сгенерированный
  секрет) — включает платформу `api_server` на `127.0.0.1:8642` при
  следующем рестарте гейтвея.
- Новый пакет `hermes-web/` в этом репозитории — деплой тем же
  способом, что и `project_index` (`rsync` на сервер, без git на
  проде).
- `hermes-web.service` — systemd user-юнит под `hermes` (по образцу
  `hermes-dashboard.service`/`hermes-gateway.service`), слушает
  `127.0.0.1:8643`, `enable --now` (linger уже включён).
- `hermes-web.db` (SQLite) — рядом с пакетом на сервере, в
  `.gitignore` (как `.env`).
