# Спек: индикация «Hermes отвечает» + кнопка STOP

Дата: 2026-08-03
Статус: approved

## Контекст

Живая жалоба пользователя: пока идёт ход (`sendMessage()` в
`project-workspace.html` ждёт SSE-поток от `POST /api/chat/{id}/send`),
повторная отправка молча блокируется — `if (sendBtn.disabled) return;`
([project-workspace.html:798](../../hermes-web/static/project-workspace.html#L798)).
Блокировка сама по себе обоснована (см. комментарий на строках 795-798:
`recoverAfterStreamDrop()` целиком перезаписывает общий массив `messages`,
гонка с параллельным `readSSE`-колбэком второго хода) — но она полностью
беззвучная: ни подсказки, что Hermes ещё работает, ни способа передумать
и прервать ход, если модель явно пошла не туда. Отсюда два независимых,
но взаимосвязанных запроса:

1. Видимая индикация «Hermes отвечает» вместо тишины.
2. Кнопка STOP, которая реально прерывает текущий ход (не просто
   перестаёт слушать поток).

Для STOP пришлось разобраться, что происходит на стороне самого Hermes
(прочитан реальный исходник `gateway/platforms/api_server.py` из
официального репозитория, не только наш `hermes-web`):

- Наш бэкенд ходит в `POST /api/sessions/{id}/chat/stream` —
  `_handle_session_chat_stream` в Hermes. Этот обработчик сам генерирует
  `run_id`, но **не** регистрирует его в `_active_run_agents`/
  `_active_run_tasks` — то есть официальный документированный
  `POST /v1/runs/{run_id}/stop` для наших сессий не сработает, он рассчитан
  на другой API-путь (`/v1/runs`), которым мы не пользуемся.
- Тем не менее сам `_handle_session_chat_stream` уже ловит обрыв
  соединения клиента: `except (asyncio.CancelledError, ConnectionResetError):
  task.cancel(); raise` — и отменяет фоновую задачу, которая крутит агента.
  То есть обрыв HTTP-запроса к Hermes **уже является** рабочим способом
  кооперативно остановить ход — тем же по духу способом, что официальный
  `/stop` («просит агента остановиться на следующей безопасной точке»,
  не мгновенно, не гарантированно прерывает уже начавшийся вызов
  инструмента).
- В нашем `hermes_web/app.py::handle_send_message` уже есть код, который
  аккуратно отменяет `pending`-задачу (ожидание `agen.__anext__()`) при
  завершении цикла ([app.py:181-187](../../hermes-web/hermes_web/app.py#L181-L187))
  — специально написан, чтобы **не** отменять её раньше времени (см.
  комментарий на строках 157-161 про риск оборвать реальный запрос ради
  заглушки). Сегодня этот путь срабатывает только при настоящем сетевом
  обрыве. STOP просто даёт пользователю осознанно вызвать тот же путь.

Рассмотренная и отклонённая альтернатива: переезд на `/v1/runs` ради
официального `stop`-эндпоинта с явным `interrupted: true` в истории —
даёт то же по сути кооперативное поведение, но требует переписать
`hermes_client.py`/`quickchat.py` и способ связывания сессии с историей
— несоразмерно ради кнопки STOP, отклонено (YAGNI).

## Feature 1 — индикация «Hermes отвечает»

Чисто фронтенд, `project-workspace.html`. Статус-строка над полем ввода
(`#composeInput`), видна всё время, пока `sendBtn.disabled === true`
(то есть пока `sendMessage()` внутри `try`), скрывается сразу после
(`finally { sendBtn.disabled = false; }` — туда же добавляется скрытие
строки).

Текст меняется по фазам через уже приходящие в `sendMessage()` SSE-события
(без новых событий с бэкенда):

- по умолчанию, до первого события — «Hermes думает…»;
- на `tool.started` / `tool.progress` с `tool_name` — «Hermes использует
  `<tool_name>`…» (тот же `payload.tool_name`, что уже уходит в
  `appendActivity`);
- на первую `assistant.delta` — строка скрывается (дальше уже видно
  печатающийся текст, дублировать незачем).

Строка сбрасывается в исходное состояние («Hermes думает…») в начале
каждого нового `sendMessage()` — иначе после первого хода с
`tool.started` она может застрять на имени старого инструмента при
следующей отправке до первого нового события.

## Feature 2 — кнопка STOP

### Фронтенд (`project-workspace.html`)

- Отдельная кнопка `⏹` (`stopBtn`) рядом с кнопкой отправки (`sendBtn`).
  Видна/активна только пока `sendBtn.disabled === true`; скрыта/неактивна
  в остальное время — то же условие, что уже управляет `sendBtn`.
- В `sendMessage()` заводится `const controller = new AbortController()`;
  сигнал передаётся в `apiFetch` (`{ signal: controller.signal }`, `apiFetch`
  в `app.js` уже прозрачно прокидывает `options` в `fetch`, изменений там не
  требуется). Клик по `stopBtn` вызывает `controller.abort()`.
- `readSSE()` при обрыве бросает `AbortError` из `reader.read()` — уже
  попадает в существующий `catch (err) { streamEndedCleanly = false; }`
  ([project-workspace.html:869-871](../../hermes-web/static/project-workspace.html#L869-L871)).
  Добавляется проверка `err.name === 'AbortError'` → флаг
  `stoppedByUser = true`.
- Ветвление после блока `try/catch` вокруг `readSSE`:
  - `streamEndedCleanly` (как сейчас) → `reconcileWithHistory()`.
  - `stoppedByUser` → **не** вызывается `recoverAfterStreamDrop()` (он
    рассчитан на случайный обрыв связи и ждёт/опрашивает историю до
    `MAX_WAIT_MS`, это осмысленная отмена, а не сбой сети). Вместо этого:
    к текущему (уже частично написанному) `messages[assistantIdx].content`
    дописывается `\n\n⏹ _остановлено пользователем_`, `renderMessages()`,
    и один быстрый `reconcileWithHistory()` — если Hermes всё же успел
    сохранить что-то в свою историю к этому моменту, актуальная версия
    подтянется; если нет — на экране остаётся то, что уже было отрендерено
    вживую с пометкой (см. риск ниже).
  - иначе (сеть действительно оборвалась, не `AbortError`) — как сейчас,
    `recoverAfterStreamDrop()`.
- `refreshTreeAndFiles()` вызывается во всех трёх ветках, как сегодня.

### Бэкенд (`hermes_web/app.py::handle_send_message`)

Сегодня обрыв клиентского соединения никак явно не обрабатывается:
`response.write()` после ухода клиента упадёт с `ConnectionResetError`
(или аналогом из aiohttp), это не входит в текущий
`except (quickchat.QuickChatError, hermes_client.HermesClientError,
aiohttp.ClientError, asyncio.TimeoutError)` — исключение уйдёт
необработанным, будет залогировано как трейсбек уровня ERROR несмотря на
то, что это станет штатным поведением после этой фичи (пользователь
целенаправленно жмёт STOP).

Правка: обернуть цикл записи (`while True: ... await response.write(...)`)
в отдельный `try/except (ConnectionResetError, ...)`, залогировать на
уровне `debug` («клиент прервал поток») вместо необработанного трейсбека.
Существующий `finally: if not pending.done(): pending.cancel()`
(строки 181-187) не меняется — он уже делает то, что нужно; меняется
только то, что путь до него теперь не выглядит ошибкой сервера. Точный
набор типов исключений (`ConnectionResetError` — встроенный, плюс что
реально бросает aiohttp в этой версии) уточняется в реализации по TDD —
это не то, что можно надёжно определить чтением кода, а не тестом с
реальным разрывом соединения.

### Известный риск — фиксируется, не решается в этой фиче

Ход, отменённый до того, как `_handle_session_chat_stream` на стороне
Hermes успеет отправить `assistant.completed`/`run.completed`, может не
попасть целиком в собственную историю сессии Hermes (`GET
/api/sessions/{id}/messages`, которым пользуется наш `get_history`). То
есть после перезагрузки страницы partial-ответ с пометкой «⏹ остановлено»
теоретически может исчезнуть, даже если только что был виден живьём —
ограничение самого Hermes (сохраняет ли он что-то в свою историю при
`task.cancel()` середины хода — не выяснено чтением кода API-сервера,
слишком глубоко во внутренностях `_run_agent`). Не гарантируется и не
чинится в рамках этой фичи — фиксируется как обязательный пункт живой
приёмки (проверить эмпирически на реальном сервере: остановить ход,
перезагрузить страницу, посмотреть, что осталось), а не как баг, если
подтвердится.

## Вне рамок

- Переезд на `/v1/runs` ради официального `stop`-эндпоинта с гарантией
  сохранения `interrupted: true` в истории — сознательно отклонено (см.
  Контекст), несоразмерно ради этой фичи.
- Гарантированное мгновенное прерывание уже начавшегося вызова инструмента
  (например, долгой docker-команды) — Hermes не даёт такой гарантии даже
  через официальный `/stop` («на следующей безопасной точке»), мы не можем
  дать больше, чем даёт сама платформа.
- Индикация конкретного прогресса внутри инструмента (проценты, время) —
  не запрашивалось, есть только факт «идёт `tool_name`».
