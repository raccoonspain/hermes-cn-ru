# Бэклог: находки живого тестирования рабочего экрана (2026-07-31)

**Статус:** черновик-бэклог, ждёт брейнсторминга по группам C и D перед
`writing-plans`. Группы A и B достаточно однозначны технически — можно
сразу переходить к `writing-plans`, без отдельного брейнсторма, если
пользователь подтвердит объём.

## Контекст

Сразу после деплоя D-015 пользователь прогнал `hermes.blackboxbegin.space`
живьём (создание нового проекта, `chat.html`, `project-workspace.html`) и
сформировал список из 8 находок — смесь багов и фич-запросов. Ниже —
каждая находка, привязанная к реальному коду (не гипотезы), сгруппированная
по риску/размеру дизайн-решений, с предложенным порядком реализации.

## Группа A — CRUD-гигиена (маленькие бэкенд-правки, разблокируют
дальнейшее тестирование немедленно)

### A1. Удаление проекта
**Находка:** «в ALL сейчас есть два "мусорных" проекта, которые были
тестами — не понятно, как их удалить».
**Причина:** в `hermes-plugins/project_index/core.py` нет функции
`delete_project`; в `hermes_web/app.py` нет соответствующего эндпоинта.
Опция физически отсутствует, а не просто спрятана в UI.
**Предложение:** `project_index_core.delete_project(user, project_path,
workspace_root)` — по аналогии с `move_project` (тот же слой защиты пути:
принадлежит пользователю → это вообще проект, т.е. есть `about.md`),
удаляет запись из индекса и папку с диска (`shutil.rmtree`);
`DELETE /api/projects` (тело: `path`) в `app.py`; кнопка «Удалить» в
`project-selector.html` на карточке проекта, с подтверждающим диалогом
(необратимое действие — папка со всем содержимым).
**Открытый вопрос:** мягкое удаление (переименовать в `.trash/` на
диске, восстановимо) или безвозвратное `rmtree`? Учитывая, что сценарий
использования — это в первую очередь чистка тестового мусора, но со
временем и реальные проекты, вероятно стоит мягкое перемещение в
скрытую `.trash/` папку пользователя, а не мгновенный `rmtree` — дешёвая
подстраховка от случайного клика. Решить перед `writing-plans`.

### A2. Создание проекта из списка, с привязкой к группе под курсором
**Находка:** «нужна возможность создавать проекты из листа
project-selector, определяя проект в группу, которая выделена курсором».
**Причина:** сегодня единственный способ завести проект — «Быстрый чат»
(`create_quick_chat`), который всегда кладёт в группу `ALL` и сразу же
поднимает Hermes-сессию. Отдельного «просто создать пустой проект в
группе X» пути нет.
**Предложение:** новая функция в `quickchat.py` (или прямо в
`project_index_core`) — `create_project(user, group, title, config)`:
делает то же, что и `create_quick_chat`, кроме подъёма Hermes-сессии
(она создаётся лениво при первом открытии через уже существующий
`get_or_open_session`) — то есть без сетевого вызова, значит без риска
«осиротевшего» проекта при сбое Hermes (тот же паттерн, что уже
проверен в этом проекте, см. финальное ревью 2026-07-26). Кнопка
«+ Новый проект» в `project-selector.html`, использующая
`state.group`/последнюю группу под курсором как `new_group`.
**Зависит от:** группы B (проект без папок `source/outer/result` создан
не будет — тот же хелпер бэкфилла).

### A3. Редактирование тегов
**Находка:** «не понятно, как менять теги».
**Причина:** `tags`/`status` — YAML-фронтматтер `about.md`
(`project_index_core.parse_about_md`), правится только как сырой текст
файла в редакторе — нет структурированного поля.
**Предложение:** в панели деталей проекта (`project-selector.html`,
`.panel3`) — там, где уже отображаются `p-tags`, добавить инлайн-редактор
(добавить/убрать тег как chip, переключатель `active`/`archived`) поверх
уже существующего `PUT`-эндпоинта для `about.md` (переиспользовать
`workspace.save_file` на `about.md`, собрав корректный YAML-фронтматтер
на фронтенде — не парсить/не генерировать YAML руками на сервере без
теста, риск сломать существующий frontmatter при неполном round-trip).
**Открытый вопрос:** нужно ли валидировать/подсказывать список уже
существующих тегов пользователя (автокомплит по `tagCloud`, который уже
есть в списке проектов) — небольшое дополнение, но решить перед планом.

## Группа B — Полнота скаффолда проекта (маленький, самодостаточный
бэкенд-фикс, без дизайн-вопросов)

### B1. Создавать папки source/outer/result вместе с файлами
**Находка:** «нужные файлы AGENTS.md, about.md, history.md создаются, а
папки — нет, нужно сразу заводить все файлы и дерево подкаталогов».
**Причина:** `create_quick_chat` (`hermes_web/quickchat.py:171`) делает
`os.makedirs(project_abs_path, exist_ok=True)` только для корня проекта;
`_backfill_root_files` создаёт только 3 файла. Ни один путь не создаёт
`source/`, `outer/`, `result/`.
**Предложение:** расширить `_backfill_root_files` (переименовать в
`_backfill_project_scaffold` или добавить рядом `_backfill_root_dirs`) —
`os.makedirs(os.path.join(project_root, "source"), exist_ok=True)` и
так же для `outer`/`result`; вызывать из тех же двух точек, что и
файловый бэкфилл (`create_quick_chat` + `get_or_open_session`), плюс из
новой A2. Симметрично B2 ниже — раз папки видны в дереве всегда
(`list_tree` уже отдаёт `{bucket}_dirs`, включая пустые, с D-013), пустые
`source/outer/result` будут видны сразу после создания проекта, а не
только после первого файла в них.

### B2. Корневые файлы (about.md/AGENTS.md/history.md) в общем дереве
**Статус: закрыто, работы не требует (подтверждено пользователем
2026-07-31).** В задеплоенном `project-workspace.html` эти три файла уже
отображаются отдельным блоком над `SOURCE/OUTER/RESULT` в левой панели —
находка была про уже существующее поведение, не про пробел.

## Группа C — Объединение «Быстрого чата» и рабочего экрана (среднее,
архитектурное упрощение, минимум новых дизайн-решений)

### C1. «Быстрый чат» должен открывать `project-workspace.html`, не `chat.html`
**Находка:** «При создании нового проекта окно пустое — без левой и
правой областей» (скриншот 1: `chat.html?id=...&path=...` — минимальная
однострочная колонка, нет дерева файлов слева и «Активности агента»
справа).
**Причина:** `home.html:120` шлёт на `chat.html` — отдельную, более
раннюю и урезанную страницу (наследие D-006/среза 1+2, до появления
`project-workspace.html` в D-010). `project-workspace.html` уже умеет
всё, что умеет `chat.html`, и больше — включая открытие уже
существующего чата через `path` (`/api/projects/open` = тот же
`get_or_open_session`, что использует и `create_quick_chat`).
**Предложение:** `home.html` переключить редирект на
`project-workspace.html?path=...` вместо `chat.html?id=...&path=...` —
`project-workspace.html` сама сделает `open` и получит/создаст сессию.
После переключения `chat.html` становится мёртвым кодом — удалить
файл целиком (не оставлять «на всякий случай» — правило проекта: не
хранить полуработающий дублирующий путь). Из всех находок в этом
бэклоге у этой — наименьший риск и наибольшая отдача (закрывает
находку C1 полностью и косвенно снимает часть недовольства из группы D,
т.к. `project-workspace.html` и так не использует фиксированную
760px-колонку `chat.html`).
**Проверить перед планом:** действительно ли `project-workspace.html`
корректно обрабатывает первое открытие вообще без предсозданного
`about.md`-заголовка (у `create_quick_chat` заголовок — «Новый разговор
ЧЧ:ММ», у прямого `create_project` из A2 — заданный пользователем) — не
ожидается расхождений, но стоит явно проверить в этой задаче, раз меняем
основной вход в самый частый сценарий использования.

## Группа D — Редизайн layout редактора и ширины чата (самое крупное,
нужен отдельный брейнсторминг по интеракции перед спеком)

### D1. Раздвижная область редактора вместо модального окна
**Находка:** «всплывающее окно для редактора файлов не подходит, нужно
в том же окне "раздвигать область" между областью навигации слева и
чатом справа (примерно как в VS Code)... Когда закрываешь — сворачивается
и чат расширяется обратно».
**Открытые вопросы для брейнсторма:** ширина панели редактора —
фиксированная, по перетаскиваемому разделителю (drag handle, как VS
Code) или по доле экрана; сохранять ли выбранную ширину в `localStorage`
(по аналогии с уже существующим `hermes-web:tree-expanded:` для дерева);
поведение на узких экранах/мобильном (сейчас об этом ограничении речи
не было, но 3-колоночный layout на мобильном может не влезть в принципе)
— уточнить, важен ли мобильный сценарий вообще.

### D2. Расширяемая область чата
**Находка:** «Окно чата очень узкое. Охват всего две строки... Нужно
иметь возможность расширять».
**Связь с D1:** вероятно, один и тот же layout-редизайн: сейчас чат в
`project-workspace.html` зажат в узкую колонку между левым деревом и
правой «Активностью агента» — если вводить раздвижной редактор (D1), тот
же 3(4)-панельный layout с перетаскиваемыми границами закрывает и D2
одним и тем же механизмом, а не отдельной работой. Рекомендация: **не
делать D2 отдельной задачей** — включить как часть общего решения по
layout в D1, решать вместе на одном брейнсторме.

## Рекомендованный порядок реализации

1. **Группа B** (B1 — папки при создании проекта) — сначала, потому что
   от неё зависит A2, и она полностью самодостаточна технически.
   B2 — не реализация, а уточняющий вопрос пользователю (возможно, уже
   закрыто).
2. **Группа A** (A1 удаление → A2 создание → A3 теги) — маленькие,
   независимые бэкенд+UI правки, в этом порядке — удаление сначала,
   потому что прямо сейчас блокирует уборку тестовых проектов пользователя.
3. **Группа C** (C1 — редирект «Быстрого чата» на `project-workspace.html`,
   удаление `chat.html`) — архитектурное упрощение, снимает главный «баг»
   пустого экрана и заодно облегчает почву для группы D (меньше
   диалектов layout, один экран вместо двух).
4. **Группа D** (D1+D2 вместе) — последней: самая крупная, единственная
   требующая отдельного `brainstorming` по интеракции перед `writing-plans`.
