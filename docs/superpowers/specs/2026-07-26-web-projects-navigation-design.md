> финального прочтения перед переходом к плану реализации.
>
> Продолжение `docs/superpowers/specs/2026-07-26-web-backend-auth-chat-design.md`
> (срез 1+2, реализован и выкачен). Срез 3 сам по себе разбит на две
> части: (1) — этот документ, навигация по Группам/Проектам
> (`project-selector.html`: список/поиск/фильтры/перенос); (2) —
> полноценный `project-workspace.html` (файловое дерево `source/outer/
> result`, вложения, лог активности агента) — отдельный последующий
> спек, сознательно не берём в этот раунд (кнопка «Открыть проект →»
> в этом срезе — плейсхолдер).

## Зачем

Макет `home.html` (уже задеплоен) содержит плитку «Работа с проектами»,
помеченную как `disabled`/«скоро» — этот срез её включает. Заказчик
формулирует реальный сценарий использования: за год у одного
пользователя накопится порядка 20–30 тем (групп) по 20–30 проектов в
каждой плюс папка `ALL` — то есть до **~1000 проектов в год**. Значит
экран не может работать так, как в кликабельном макете
(`/result/project-selector.html`), где список из десятка проектов
захардкожен в JS-массиве и вся фильтрация — в браузере поверх него:
нужна серверная фильтрация по времени последней активности и статусу
ещё до того, как данные попадут на клиент.

## Проверено в текущем коде (важно)

Перед спеком перечитан `hermes-plugins/project_index/core.py` и
`storage.py` (уже реализованы и выкачены, под-проект A):

- `parse_about_md` сейчас разбирает только `title`/`description`/`tags`/
  `status` — секции «Опорные точки» и «На чём остановились» (обе
  существуют в реальных `about.md`, их пишет `quickchat.py` с самого
  среза 1+2) не извлекаются.
- Таблица `projects` в `index.db` хранит `path`/`title`/`tags`/`status`/
  `embedding`/`updated_at` — **без `description`**. `updated_at`
  сейчас = момент вызова `index_update` (`datetime.utcnow()`), не время
  реальной правки `about.md` — при повторном `reindex_all` без всяких
  изменений `updated_at` всё равно «освежается», что ломает семантику
  «последняя активность».
- Прямого способа перечислить все проекты пользователя одним SQL-
  запросом с фильтром по времени/статусу нет — есть только
  `list_projects_for_user` в `storage.py` (без фильтров, забирает всё) и
  `reindex_all` в `core.py` (обходит диск, а не SQL).
- `move_project` уже полностью реализован и покрыт тестами — можно
  использовать как есть.
- Групп как отдельной сущности с метаданными (красивое имя, эмодзи,
  закреплённость) нигде не существует — на диске «группа» это просто
  имя папки `workspace/<user>/<группа>/`.
- `home.html` (реально задеплоенный, не макет) уже содержит закомментированную
  под будущее плитку «Работа с проектами» (`disabled`, ведёт в `#`) и
  плитку «Искать по всем темам» (тоже `disabled`) — обе включаются этим
  срезом.

## Архитектура

Без нового стека — тот же `hermes-web` (Python/aiohttp), та же прямая
интеграция с `project_index/core.py` без похода через LLM. Три
источника данных:

1. **Проекты для списка** — SQL-таблица `projects` в `index.db`
   (`project_index`), расширенная колонкой `description` и с
   переопределённым `updated_at` (mtime `about.md`, не время индексации).
   Новая функция `list_projects_for_user(user, workspace_root, db_path,
   updated_since=None, status=None)` в `core.py` — читает **только SQL**,
   без похода на диск, поэтому остаётся быстрой при тысячах строк.
2. **Детали одного проекта** (для панели `about.md` — «Опорные точки» +
   «На чём остановились», которые сознательно не индексируются и не
   попадают в SQL, см. `hermes-prj-structure.md`) — новая функция
   `get_project_detail(user, project_path)` в `core.py`, единственное
   место в этом срезе, где `about.md` читается с диска, и только по
   клику на конкретный проект, не при построении списка.
3. **RAG-поиск** («похожие по смыслу») — уже готовый
   `core.search_similar(user, query)`, без изменений.

Новая таблица `group_meta` в `hermes-web.db` (не в `index.db` —
метаданные групп это собственность веб-морды, а не индекса): `user`,
`slug` (= имя папки на диске, канонический id группы, никогда не
переименовывается при редактировании), `display_name`, `emoji`,
`pinned`, `created_at`. У группы без строки в `group_meta` (например,
`ALL` до первой правки) имя по умолчанию — сам `slug`, без эмодзи, не
закреплена.

## Изменения в `project_index/core.py` и `storage.py`

- `parse_about_md` — дополнительно извлекает `points` (секция «Опорные
  точки») и `now` (секция «На чём остановились»); обе необязательные —
  пустая строка, если секции нет или она пуста (в отличие от `title`/
  `description`, отсутствие которых по-прежнему `ProjectIndexError`).
- `storage.init_db` — добавляет колонку `description TEXT NOT NULL
  DEFAULT ''` в `projects` (через `ALTER TABLE ... ADD COLUMN`, с
  проверкой что колонки ещё нет — `index.db` на сервере уже существует
  и содержит реальные строки, дропать/пересоздавать нельзя).
- `storage.upsert_project` — принимает и сохраняет `description`.
- `core.index_update` — передаёт `about["description"]` в
  `upsert_project`; `updated_at` берёт из `os.path.getmtime(about_path)`
  (переводит в ISO через `datetime.utcfromtimestamp`), а не из
  `datetime.utcnow()`.
- `storage.list_projects_filtered(conn, workspace_root, user,
  updated_since=None, status=None)` — SQL `WHERE path LIKE
  '<workspace_root>/<user>/%' AND (updated_at >= ? OR ? IS NULL) AND
  (status = ? OR ? IS NULL)`, группа для каждой строки выводится из
  `path` (второй компонент после `<user>/`).
- `core.list_projects_for_user(user, workspace_root=WORKSPACE_ROOT,
  db_path=DB_PATH, updated_since=None, status=None)` — тонкая обёртка
  над `storage.list_projects_filtered`, `updated_since` — `datetime`
  или `None`.
- `core.get_project_detail(user, project_path, workspace_root=
  WORKSPACE_ROOT)` — резолвит путь (`resolve_project_path`, уже есть),
  читает `about.md` (`_read_about`, уже есть, теперь возвращает и
  `points`/`now`), добавляет `group` (родительская папка) и `path`.

Существующие вызовы `index_update`/`move_project`/`reindex_all` из уже
задеплоенного кода (в т.ч. `quickchat.py`) не меняют сигнатуру — только
поведение `updated_at` (с этим полем сегодня никто не работает за
пределами этого среза).

## Данные (`hermes-web.db`)

```sql
CREATE TABLE group_meta (
    user TEXT NOT NULL,
    slug TEXT NOT NULL,
    display_name TEXT NOT NULL,
    emoji TEXT NOT NULL DEFAULT '',
    pinned INTEGER NOT NULL DEFAULT 0,
    created_at TEXT NOT NULL,
    PRIMARY KEY (user, slug)
);
```

## API (`hermes-web`, все эндпоинты — под активной веб-сессией)

- **`GET /api/groups`** — папки `workspace/<user>/*` (`ALL` всегда
  присутствует, даже если пустая) join с `group_meta` по `slug`; для
  каждой — `{slug, display_name, emoji, pinned, project_count}`.
- **`POST /api/groups {name, emoji}`** — слаг = транслитерированное
  (RU→EN) и урезанное имя в kebab-case, при коллизии — числовой суффикс
  (`dom-i-remont-2`); создаёт папку `os.makedirs(..., exist_ok=False)`
  на диске + строку в `group_meta`.
- **`PUT /api/groups/{slug} {display_name?, emoji?, pinned?}`** — upsert
  в `group_meta` (группа могла не иметь строки, например `ALL`); папку
  на диске не трогает.
- **`GET /api/projects?group=<slug>|*&since=week|month|quarter|
  half_year|year|all&status=active|archived|all`** — обёртка над
  `list_projects_for_user`; `group=*` — без фильтра по группе («искать
  везде»); при отсутствии `since`/`status` бэкенд подставляет
  `month`/`active` (тот же дефолт, что и фронт всегда шлёт явно —
  двойная защита, чтобы прямой вызов API без параметров тоже не
  пытался вычитать всю тысячу строк).
- **`GET /api/projects/detail?path=...`** — обёртка над
  `get_project_detail`; 404, если путь не резолвится в пространство
  пользователя или `about.md` не найден.
- **`POST /api/projects/search {query}`** — обёртка над
  `search_similar`; при недоступном wormsoft.ru отдаёт `{results: [],
  message: "..."}`  как есть (не 500).
- **`POST /api/projects/move {path, new_group?, new_name?}`** — обёртка
  над `move_project`; ошибки `ProjectIndexError` (коллизия имени и
  т.п.) — 400 с текстом сообщения.

Все эндпоинты валидируют, что `path`/`group` принадлежат текущему
пользователю сессии (переиспользуем `resolve_project_path`, который уже
это делает и уже кидает `ProjectIndexError` при выходе за пределы) —
никаких новых проверок изоретать не нужно.

## Фронтенд (`project-selector.html`)

Берём кликабельный макет `/result/project-selector.html` почти как
есть — вся логика поиска/тегов/закрепления/размера плиток уже на чистом
JS без сборки, как и в `login.html`/`home.html`/`chat.html` из среза
1+2. Меняется:

- Начальные данные (`groups`, `projects`) — не захардкожены, а
  приходят из `GET /api/groups` и `GET /api/projects?...`.
- Новый ряд фильтров «давность»: неделя / месяц / квартал / полгода /
  год / без ограничения — рядом с уже существующим `active`/`archived`/
  `all`. Оба идут в query-параметрах запроса к `/api/projects`
  (серверная фильтрация); теги и текстовый поиск по уже полученному
  срезу — как в макете, на клиенте.
- **По умолчанию при заходе на страницу** — `since=month&status=active`.
  Явно требуется заказчиком, чтобы страница нормально грузилась и не
  пыталась разом вытащить проекты за весь год.
- «Настроить группу» → `POST`/`PUT /api/groups/...` вместо мутации
  локального массива.
- «Перенести в другую группу» (в макете кнопка без обработчика) —
  добавляется маленький попап со списком групп (переиспользует уже
  загруженный `groups`), выбор → `POST /api/projects/move` → обновление
  списка и закрытие панели.
- «Открыть проект →» — остаётся плейсхолдером (`alert`/отключена),
  полноценный `project-workspace.html` — отдельный следующий спек.
- Панель `about.md` при клике на проект — сначала показывает уже
  известные из списка поля (title/description/tags/status), затем
  подгружает `GET /api/projects/detail` и дополняет «Опорные точки»/«На
  чём остановились» (может занять доли секунды на большом проекте —
  не блокирует открытие панели).
- Плитка «Работа с проектами» в `home.html` — убирается `disabled`,
  ведёт на `project-selector.html`. Плитка «Искать по всем темам» —
  убирается `disabled`, ведёт на `project-selector.html#everywhere`
  (якорь уже обрабатывается в макете).

## Обработка ошибок

- Истёкшая/невалидная кука — 401 → редирект на `/login`, как во всех
  остальных эндпоинтах среза 1+2 (`requireAuth`/`apiFetch` уже это
  умеют, переиспользуются без изменений).
- `POST /api/projects/move` на несуществующий путь/коллизию имени в
  целевой группе → 400 с текстом `ProjectIndexError`, фронт показывает
  как есть.
- `POST /api/groups` с именем, дающим слаг-коллизию с уже существующей
  группой → не ошибка, просто дедуп-суффикс — молча.
- wormsoft.ru недоступен при RAG-поиске → `{results: [], message:
  "поиск временно недоступен"}`, не 500 (как уже сделано в
  `search_similar`).
- `GET /api/projects/detail` на путь вне пространства пользователя или
  без `about.md` → 404, без деталей причины.

## Автоархивация «старше года»

Заказчик упомянул идею — со временем либо командой Гермесу проставлять
`status: archived` всем проектам старше года, либо делать это вручную.
**Не входит в этот срез** (сам заказчик обозначил как «можно потом»)
— возможный будущий пункт `docs/state.md`, отдельная задача.

## Тестирование

- `project_index`: юнит-тесты на `parse_about_md` (новые секции
  `points`/`now`, включая случай отсутствующих/пустых), на
  `list_projects_filtered`/`list_projects_for_user` (фильтры по времени
  и статусу, включая границы диапазонов), на `index_update` (что
  `updated_at` берётся из mtime файла, а не из времени вызова — в т.ч.
  повторный вызов без изменения файла не должен менять `updated_at`),
  на `storage.init_db` (миграция существующей базы без колонки
  `description` не падает, дописывает колонку). Существующие тесты
  `move_project`/`reindex_all`/`search_similar` не должны сломаться.
- `hermes-web`: юнит-тесты на `/api/groups` (create/list/update,
  слаг-дедуп, транслитерация), `/api/projects` (фильтры since/status/
  group, дефолты при отсутствии параметров), `/api/projects/move`
  (успех + 400 на коллизию), `/api/projects/search` (мок
  `search_similar`, в т.ч. кейс недоступного wormsoft.ru), `/api/
  projects/detail` (404 на чужой путь). Hermes/project_index мокаются
  так же, как уже сделано для `quickchat.py` в срезе 1+2.
- После деплоя — ручной приёмочный тест на `hermes.blackboxbegin.space`:
  зайти в «Работа с проектами», убедиться что уже созданные через
  «Быстрый чат» и мигрированный `physics-tasks` проекты видны с
  правильными полями, создать новую группу, перенести в неё проект,
  перезагрузить страницу и убедиться что группа и перенос сохранились,
  проверить что смена фильтра «давность» меняет список.
