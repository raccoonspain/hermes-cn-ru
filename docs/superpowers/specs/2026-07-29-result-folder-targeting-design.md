# Спек: видимость пустых папок result/ и явный выбор целевой папки для результата

**Дата:** 2026-07-29 · **Статус:** согласовано с пользователем, ждёт спек-ревью

## Контекст

Живой прогон (разбор задач Кирика, 2026-07-29) показал две связанные
проблемы рабочего экрана проекта (`project-workspace.html`):

1. Пользователь создал через UI подпапку `kirik` внутри `result/`, но она
   не отображается в дереве файлов.
2. Модель почти всё складывает в раздел «остальное» (вне
   `source/outer/result`), хотя системное сообщение уже просит класть
   готовые файлы в `result/` (см. `_system_message_for` в
   `hermes_web/quickchat.py`). В `result/` не падает ничего.

Пользователь работает с разными источниками контекста в одном проекте
(разные разделы учебника, разные темы) и хочет разделять результаты по
подпапкам, а не сваливать всё в одну кучу — отсюда и создание `kirik`.

## Проблема 1: пустые папки не видны

`list_tree` (`hermes_web/workspace.py:162-188`) строит секции
`source`/`outer`/`result` только из **файлов**, найденных `os.walk`.
Директория, в которой нет ни одного файла, физически не порождает ни
одной записи в ответе — она невидима для API целиком, а не только для
интерфейса.

Фронтенд отчасти компенсирует это переменной `manuallyCreatedFolders`
(`project-workspace.html:188`) — JS `Set`, живущий только в памяти
открытой вкладки. Он и создаёт иллюзию, что папка "работает" сразу после
создания, и объясняет, почему она пропадает: после перезагрузки страницы,
в другой вкладке или с другого устройства сервер по-прежнему не знает,
что папка существует.

### Решение

`list_tree` при обходе каждого bucket'а дополнительно собирает список
самих директорий (не только файлов в них), включая пустые:

```python
def list_tree(user: str, project_path: str, config) -> dict:
    ...
    for bucket in BUCKETS:
        bucket_dir = os.path.join(project_root, bucket)
        entries = []
        dirs = []
        if os.path.isdir(bucket_dir):
            for dirpath, _dirnames, filenames in os.walk(bucket_dir):
                if dirpath != bucket_dir:
                    dirs.append(os.path.relpath(dirpath, project_root))
                for filename in filenames:
                    full = os.path.join(dirpath, filename)
                    entries.append({...ка и сейчас...})
        tree[bucket] = sorted(entries, key=lambda e: e["relative_path"])
        tree[f"{bucket}_dirs"] = sorted(dirs)
    ...
```

Фронтенд (`buildFolderTree`, `renderFolderOptions`) переключается на
`tree[f"{bucket}_dirs"]` как источник правды о существующих папках вместо
вывода их из путей файлов + `manuallyCreatedFolders`. Переменную
`manuallyCreatedFolders` и связанный с ней код убираем целиком — она
становится не нужна, а держать мёртвый обходной путь рядом с настоящим
источником данных — источник будущих рассинхронизаций.

Это чинит проблему полностью и на уровне данных: папка видна сразу после
создания, переживает перезагрузку страницы, видна с другого устройства
или в другой вкладке — потому что теперь это не клиентское состояние, а
факт, который отдаёт сам сервер.

## Проблема 2: модель не кладёт результаты в result/

Единственный механизм, направляющий модель в `result/` — одна фраза в
системном сообщении (`_system_message_for`,
`hermes_web/quickchat.py:161-178`), общая для всех проектов и не
привязанная к конкретному ходу. Это мягкая подсказка без обратной связи:
модель либо следует ей, либо нет, и ничего в текущем потоке не усиливает
её для конкретного хода.

**Важное ограничение** (согласовано с пользователем): технически
заблокировать запись модели мы не можем. Файловые инструменты Hermes
(`write_file` и т.п.) исполняются самим агентом Hermes внутри его
Docker-песочницы напрямую на смонтированной файловой системе — `hermes_web`
в этот процесс не встроен и не может ни перехватить, ни отклонить
конкретную запись, только прочитать результат постфактум через
`list_tree`. Значит единственный доступный рычаг — то, что мы говорим
модели в системном сообщении на этот конкретный ход, а не техническое
ограничение.

### Решение: явный выбор целевой папки + усиленная инструкция на ход

Новая строка в композере чата (`project-workspace.html`), зеркалящая уже
существующую «папка для вложений»:

```html
<div class="upload-target-row">
  <span>папка для результата:</span>
  <select id="resultTargetSelect"></select>
</div>
```

- Опции: `result` (корень, дефолт) + все подпапки из `tree.result_dirs`
  (появившегося в решении Проблемы 1) — включая пустые, значит и `kirik`
  сразу попадёт в список.
- Выбор запоминается в `localStorage`, ключ включает `projectPath` —
  подтверждено пользователем: при частых возвратах к одному и тому же
  проекту/теме не нужно выбирать заново каждый раз.
- При отправке сообщения (`sendMessage` в `project-workspace.html`)
  текущее значение селектора уходит в теле запроса:
  `POST /api/chat/{id}/send` → `{text, result_target}`.

**Бэкенд:**

- `handle_send_message` (`hermes_web/app.py:113-119`) читает
  `body.get("result_target")` (опционально, `Optional[str]`) и передаёт
  дальше в `quickchat.send_message`.
- `quickchat.send_message` (`hermes_web/quickchat.py:181`) получает новый
  необязательный параметр `result_target: Optional[str] = None` и
  передаёт его в `_system_message_for`.
- `_system_message_for(project_path, result_target=None)`: если
  `result_target` задан и проходит валидацию (см. ниже), добавляет к
  системному сообщению отдельным абзацем:

  > «Пользователь указал целевую папку для результата этого хода:
  > `{project_path}/{result_target}`. Клади готовые файлы именно туда.
  > Если считаешь, что это не подходящее место для результата этого
  > хода — спроси пользователя перед сохранением, а не сохраняй молча в
  > другое место.»

- **Валидация `result_target`** на бэкенде: должен быть ровно `"result"`
  либо начинаться с `"result/"`, без `..`-сегментов (простая проверка по
  регэкспу/сплиту пути, не файловый доступ — это лишь текст, идущий в
  промпт, а не операция с файловой системой). Если значение не проходит
  проверку или не передано вовсе — тихо не добавляем абзац, откатываемся
  к прежнему обобщённому тексту про `result/`. Ничего не падает, чат не
  прерывается.

## Что не делаем

- Не пытаемся технически заблокировать или перехватить запись модели —
  согласовано с пользователем, это прямое следствие архитектуры Hermes
  (см. выше).
- Не добавляем отдельную кнопку "создать новую папку" внутри самого
  селектора — она уже есть в дереве файлов (`＋папка` у `result` и его
  подпапок), после фикса Проблемы 1 созданная там папка сразу появится и
  в дереве, и в списке опций селектора.
- Не расширяем `result_target` на `source`/`outer` — селектор
  «папка для вложений» уже покрывает эти два bucket'а для файлов,
  загружаемых человеком; `result_target` — только про то, куда агент
  кладёт свои готовые результаты.

## Тесты

- `hermes_web/tests/test_workspace.py`: `list_tree` возвращает
  `{bucket}_dirs` с пустой подпапкой, созданной только через `make_dir`
  (без единого файла внутри) — для каждого из `source/outer/result`.
- `hermes_web/tests/test_quickchat.py`:
  - `_system_message_for`/`send_message` с валидным `result_target`
    содержит усиленный абзац с правильным абсолютным путём;
  - с `result_target=None` (или отсутствует) — прежнее поведение без
    нового абзаца;
  - с невалидным `result_target` (`"../etc"`, `"source/x"`,
    `"result/../.."`) — тихо игнорируется, без исключения.
- Ручная проверка в браузере (не юнит-тест): создать пустую подпапку в
  `result/` через `＋папка`, перезагрузить страницу — папка на месте и
  выбирается в новом селекторе; отправить сообщение с выбранной
  подпапкой — модель получает системное сообщение с абсолютным путём
  именно к ней.

## Деплой

Тот же порядок, что и в предыдущих срезах веб-морды: `rsync` изменённых
файлов `hermes_web/*.py` и `static/project-workspace.html` на сервер,
`systemctl --user restart hermes-web.service`, проверка `journalctl` на
чистый рестарт без трейсбеков.
