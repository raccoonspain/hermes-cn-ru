## 2026-07-25 — Embeddings-индекс и перенос проекта (продолжение дизайна архитектуры)
- Дизайн технической реализации embeddings-поиска похожих проектов:

  инструмента через `ctx.register_tool` — `project_index_update` и
  `project_search_similar`, плюс `project_reindex_all` для бэкфилла.
  Хранилище — обычная SQLite-таблица + brute-force cosine на numpy, не
  `sqlite-vec`/внешняя vector DB (меньше движущихся частей на VPS без
  root). Модель эмбеддингов — уже выбранная в D-001
  `qwen/qwen3-embedding:8b`. Эмбеддится только Название+Описание+tags

  `project_move` в том же плагине — и агент по команде в чате, и
  будущий веб-бэкенд вызывают одну и ту же логику. Коллизия имён —
  ошибка, без тихого авто-переименования; дата-префикс `ГГГГ-ММ-ДД_`
  снимается при выходе из `ALL` и добавляется при входе обратно;
  embedding пересчитывается всегда; индекс хранит путь как единственный

  wormsoft.ru не блокировала операцию.
- Оба раздела дописаны в [hermes-prj-structure.md](./hermes-prj-structure.md).

## 2026-07-24 — Починили доставку файлов в чат (host-visible output mount)
- Заказчик попросил агента прислать готовый файл вложением — не
  получилось (`Skipping unsafe MEDIA directive path: /workspace/...`).
- Разобрали до первопричины: `terminal`/`execute_code` работают внутри
  Docker-песочницы, её `/workspace` физически не существует на хосте
  как таковой (отдельный bind-mount) — доставка вложений резолвит путь
  на хосте и просто не находит файл. `write_file`, для сравнения, и так
  всегда пишет напрямую на хост (с проверкой `HERMES_WRITE_SAFE_ROOT`) —
  не подвержен этой проблеме, если использовать относительные пути.
- Настроили официально рекомендуемый Hermes'ом host-visible output
  mount: `/output` внутри контейнера → `~/.hermes/cache/documents` на
  хосте (это уже входит в список директорий, которые доставка вложений
  считает безопасными).
- По пути наткнулись на баг/недоработку: `terminal.docker_volumes` в
  `config.yaml` не бриджится в `TERMINAL_DOCKER_VOLUMES` — похоже,
  из-за нашей устаревшей версии config schema (v0 вместо актуальной 33).
  Обошли тем же приёмом, что и с `WORMSOFT_API_KEY` раньше — прописали
  переменную напрямую в `.env`. Проверено вживую: запись/чтение через
  `/output` работает, файл виден на хосте.
- Пересоздали старые persistent-контейнеры (Docker крепит тома только
  при создании, на лету новый маунт не подхватить).
- Добавили инструкцию в `docs/manual.md`: чтобы файл гарантированно
  дошёл вложением, просить агента сохранять именно в `/output/...`.
- Связанные решения: D-004 (доп. про host-visible output mount)

## 2026-07-24 — Готовые файлы «потерялись»: путаница sandbox-workspace vs дашборд
- Агент успешно сделал 14 файлов (разбор всех 12 задач в HTML со схемами
  + архив) и отчитался «готово», но заказчик не нашёл их в разделе FILES
  дашборда — там было пусто.
- Причина: `terminal.backend: docker` — рабочая папка агента физически
  живёт в `~/.hermes/sandboxes/docker/<профиль>/workspace/` на хосте, а
  дашборд показывает совсем другую директорию — write-safe-root
  (`~/hermes/workspace`, по умолчанию пустая). Это два независимых пути,
  Hermes их не связывает автоматически.
- Нашли файлы на диске, скопировали в write-safe-root — сразу появились
  в дашборде. Задокументировали в `docs/manual.md` («Агент создал файлы,
  но их нигде нет») — на будущее самый простой обходной путь: просить
  агента присылать результат архивом прямо в чат, а не искать на диске.
- Кстати, ровно об этом Hermes предупреждает при каждом старте gateway:
  `Docker backend is enabled ... no explicit host-visible output mount
  configured ... MEDIA file delivery can fail for container-local paths`
  — мы это предупреждение видели весь день, но руки дошли осознать его
  смысл только сейчас. Возможный постоянный фикс — настроить явный
  host-visible output mount — не сделан, отложен как отдельный шаг.
