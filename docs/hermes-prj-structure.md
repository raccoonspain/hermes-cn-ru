# Файловая архитектура проектов Hermes — «Сессия это проект»

> Дизайн от 2026-07-25. Первый набросок — от заказчика (диаграмма + таблица
> структуры папки, скриншотами). Здесь — согласованная и дополненная версия
> после совместного разбора (что дублирует штатный Hermes, что нет — см.
> ниже, — и трёх раундов уточняющих вопросов).
>
> **Не привязана к каналу общения** (Matrix отменён, см. `decisions.md`
> D-008; переходим на веб, потом Android) — это только про то, как Hermes
> хранит и организует файлы/знания по темам, независимо от того, откуда
> пришёл запрос.
>
> **Статус:** дизайн согласован, реализация не начата.

## Зачем

Каждая сессия с Hermes — потраченное время и токены; результаты должны
быть переиспользуемы, а не теряться. Требование заказчика: через месяц
или год, среди десятков тысяч сессий, должно быть можно найти нужную —
минимум через группировку по темам, в идеале — через смысловой поиск.

## Проверено по официальной документации Hermes (важно)

Перед тем как проектировать своё — сверились с официальными доками/репо
(правило `CLAUDE.md`), нет ли этого уже готового:

- `project_create`/`project_list`/`project_switch` — **не существуют**.
  Единственное, что в Hermes называется «Projects» — сайдбар в Desktop-
  приложении, и это просто сканирование локальных git-репозиториев
  (`repo_scan_roots`), не про темы/знания.
- `memory` (`MEMORY.md`/`USER.md`) — два плоских глобальных файла,
  инжектятся в system prompt целиком. Не про отдельные темы/проекты.
- `session_search` — keyword-поиск (SQLite FTS5) по тексту сообщений.
  Не смысловой.
- Веб-дашборд (`hermes-dashboard`, уже поднят на сервере) — список
  сессий плоский, без группировки по темам/проектам.

**Вывод: дублирования нет** — ничего из этого не закрывает задачу.
Единственное реальное пересечение — context-файлы (`AGENTS.md` и т.п.):
Hermes сам подхватывает их из текущей рабочей директории и вложенных
папок, штатным механизмом context-discovery. На это и опирается
дизайн ниже.

## Пространство путей

```
workspace/
  <user>/
    ALL/
      ГГГГ-ММ-ДД_краткое-название/
    <Группа>/
      <Проект>/
```

- **Per-user.** У каждого пользователя (заказчик, сын — роль «Блок
  знаний») — своё отдельное пространство групп, не общее. Сценарии
  использования у них разные, смешивать темы одного с другим не нужно.
- **`ALL`** — отстойник для разового/неразобранного. Название с датой
  впереди сохраняет хронологию даже без темы.
- Перенос проекта из `ALL` в группу (или между группами) — обычная
  операция в любой момент, не только при создании (`mv` + обновление
  метаданных), см. «Жизненный цикл сессии» ниже.

## Иерархия конфигурационных файлов — не путать

- **`SOUL.md`** — один файл, `~/.hermes/SOUL.md` (`HERMES_HOME`).
  Глобальный, один на весь инстанс, **над всеми** проектами и
  пользователями сразу. Личность агента, тон, правила безопасности
  (см. `decisions.md` D-004). Не создаётся и не дублируется на проект.
- **`AGENTS.md`** — per-project, лежит в каждой `<Проект>/`. Hermes сам
  подхватывает его штатным механизмом context-discovery по мере захода
  в директорию.
- **Приоритет:** `AGENTS.md` проекта **дополняет** поведение агента
  (конвенции, специфика темы), но **никогда не переопределяет** правила
  безопасности из `SOUL.md`. Прописать это явно в шаблоне `AGENTS.md`,
  чтобы агент не пытался разрешить конфликт в свою пользу.

## Структура папки `<Проект>/`

| Путь | Назначение |
|---|---|
| `/AGENTS.md` | Конвенции проекта: что тут делаем, какими инструментами, с какими ограничениями/проблемами столкнулись и как решили, дальнейшие планы. Дополняет `SOUL.md`, не переопределяет его. |
| `/history.md` | Детальная история вниз, формат «вопрос → ответ» или «предложено → сделано». Не вся переписка — только то, что однозначно описывает суть. Ссылки на файлы человека/агента — сюда же. |
| `/about.md` | Индекс проекта, см. поля ниже. |
| `/source` | Файлы, направленные человеком. |
| `/outer` | Файлы, которые агент **нашёл** сам (не сгенерировал) — важно отделять от результатов агента. |
| `/result` | Файлы, которые агент **сгенерировал**. |

Конвенция именования в `/source` и `/outer`/`/result`: префикс датой
сессии (`2026-07-25_scan1.jpg`) — иначе повторные сессии по одному
проекту перезатирают файлы друг друга (`img1.jpg` вчера ≠ `img1.jpg`
сегодня).

### `about.md` — шесть полей

Исходные четыре блока от заказчика + два добавленных в этом разборе
(`tags`, `status`) — согласовано.

```markdown
---
tags: [excel, работа]        # НОВОЕ. Тема на стыке нескольких групп —
                              # тегами, а не дублированием папки
status: active                # НОВОЕ. active | archived
---

# Название проекта
50–80 символов, уникальное, отличает один проект от другого.

# Краткое описание
До 255 символов. Заполняется и обновляется агентом по ходу работы,
отражает суть — что тут делается.

# Опорные точки
Краткие выжимки из history.md, чтобы по одному about.md было понятно,
как развивался проект (ссылки на history.md — тоже сюда).

# На чём остановились
Последняя пара запрос → решение. Или просто запрос, если решения ещё
не было. Это же поле закрывает «чем всё закончилось» в веб-интерфейсе
(см. ниже) — для активного проекта это текущая точка, для archived —
итог.
```

**`status`** нужен, чтобы список групп/проектов в будущем UI и
embeddings-поиск не зарастали мёртвыми темами за годы использования.
Проставляется вручную или агентом по явной команде («заверши проект»).

### `history.md` — формат и ротация

- Append-only, вниз, «вопрос → ответ» / «предложено → сделано».
- **Триггер записи:** после каждого принятого решения, сгенерированного
  файла, отвеченного нетривиального вопроса — по духу того же правила,
  что уже работает в `CLAUDE.md` этого репозитория («после каждого
  осмысленного шага»).
- **Ротация:** когда файл превышает ~200 записей (или по явной просьбе
  «сожми историю») — старые записи сворачиваются в один абзац-саммари
  наверху файла, свежий хвост (последние ~20 записей) остаётся как
  есть без изменений. Без этого правила долгоживущий проект (месяцы
  общения) раздувает файл до неподъёмного для чтения/инжекта размера.

## Жизненный цикл сессии

Финальная версия — упрощена относительно первого черновика, чтобы не
добавлять диалог на каждый старт сессии:

1. **Группа не указана явно** → сессия сразу создаётся в `ALL`
   (`ГГГГ-ММ-ДД_название`). Без вопросов агенту.
2. **Группа указана явно** → проект создаётся прямо в этой группе.
3. **Явная просьба «поищи похожие темы»** → только тогда агент делает
   embeddings-поиск по `about.md` (описание + tags) в пространстве
   **этого** пользователя, показывает top-k кандидатов с кратким
   описанием, человек выбирает номер или «новый проект».
4. **Перенос между `ALL` и группами** — обычная операция по команде в
   любой момент, не только при создании.

Механизм сопоставления «на глаз» агентом при каждом новом сообщении —
сознательно убран: основной способ понять, было ли что-то похожее —
человек, через веб-интерфейс (ниже), а не агент на старте каждой
сессии.

## Перенос проекта между `ALL`/группами (`project_move`)

Согласовано 2026-07-25. Сценарий из будущего веб-интерфейса: на карточке
проекта (в `ALL` или в именной группе) — кнопка «перенести», выбор новой
группы (существующей или новой) + опционально новое имя проекта.
Иерархия остаётся двухуровневой (`<Группа>/<Проект>`, без промежуточного
уровня — уточнили отдельно).

**Кто выполняет.** Один инструмент в том же Hermes-плагине, что и
`project_index_update`/`project_search_similar` (см. выше) —
`project_move(project_path, new_group=None, new_name=None)`. И агент по
команде в чате, и веб-бэкенд (через тот же вызов, например `hermes`
CLI/API) используют один и тот же код — никакой отдельной логики переноса
на стороне веб-сервиса, чтобы не разойтись с тем, что делает агент.

**Что делает `project_move`:**
1. Проверяет, что целевой путь свободен (папка с таким именем в целевой
   группе ещё не существует) — при коллизии возвращает ошибку, **не**
   переименовывает автоматически (тихий авто-суффикс сбивает с толку —
   человек должен явно решить, как назвать).
2. Если целевая группа не существует — создаёт её (`mkdir`), в духе
   исходного «или создаёшь группу».
3. Физически переносит папку проекта (`mv`/`shutil.move`).
4. Если передано `new_name` — переименовывает папку и обновляет поле
   «Название проекта» в `about.md` соответственно (держим папку и
   `about.md` в согласии, а не расходящимися).
5. При выходе из `ALL` в именную группу — по умолчанию убирает
   дата-префикс `ГГГГ-ММ-ДД_` из имени (он был нужен только для
   хронологии внутри отстойника). При обратном переносе **в** `ALL` —
   наоборот, дата-префикс добавляется, если его ещё нет.
6. **Всегда пересчитывает embedding** (вызывает `project_index_update`
   на новом пути), даже если менялась только группа, а не имя — дешевле
   и надёжнее, чем условная логика «пересчитывать только если
   переименовали»; путь — ключ в индексе, при простом обновлении ключа
   без пересчёта легко словить рассинхрон.

**Порядок важнее атомарности.** Сначала физический перенос на диске,
потом обновление индекса. Если после переноса запрос к wormsoft.ru
(эмбеддинг) не прошёл — папка всё равно на новом месте и рабочая, просто
временно не проиндексирована до следующего `project_reindex_all`.
Обратное — заблокировать перенос из-за недоступности индекса — было бы
хуже: физическая структура должна быть источником истины, а не
подстраиваться под доступность стороннего API.

**Индекс без отдельного поля «группа».** В таблице (`project-index`)
хранится сам путь как ключ — группа/пользователь **не** дублируются
отдельными колонками, а вычисляются разбором пути при чтении. Если
кто-то перенесёт папку руками (в обход `project_move`) — путь на диске
всё равно останется источником истины, не разойдётся с отдельно хранимым
полем.

**Активная сессия.** Пути меняются — активную Hermes-сессию, привязанную
к старому `cwd`, придётся перезапускать. Открытый вопрос для дизайна
самой веб-морды (не решаем здесь): как веб-бэкенд узнаёт, что нужно
завершить/перезапустить сессию после `project_move` — например,
`project_move` может возвращать флаг `session_restart_required: true`
пользователю UI как явный сигнал.

## Навигация — человеком, не агентом

Основной способ находить прошлые темы через месяцы/годы — **не** agent-
side matching, а браузинг человеком через будущий веб-интерфейс (часть
задачи из `decisions.md` D-008 — «веб-морда на HTTPS», отдельная не
проработанная пока задача). Если человек сам нашёл нужный проект в UI —
агенту вообще не нужно ничего сопоставлять.

Требования к этому UI (для будущей реализации — сейчас не строим,
фиксируем как требования):

- Список Групп (per-user), каждая раскрывается в список Проектов.
- На карточке/строке проекта: Название, Краткое описание, «На чём
  остановились» (= «чем всё закончилось» для завершённых), `tags`.
- Фильтр по `status` (например, `archived` скрыт по умолчанию).
- Точка входа для явного embeddings-поиска («поискать похожие темы») —
  используется только когда браузинг не помог, не как дефолт.

## Embeddings-индекс — техническая реализация

Согласовано 2026-07-25, после разбора того, что даёт Hermes из коробки
для расширения инструментами (не только хуками).

### Стек

- **Модель эмбеддингов** — уже выбрана в `decisions.md` D-001:
  `qwen/qwen3-embedding:8b` через wormsoft.ru, `POST /api/gpt/embedding`
  (см. `wormsoft-api.md`). Единственная доступная модель на подписке.
- **Хранилище векторов** — обычная SQLite-таблица (не `sqlite-vec`, не
  внешняя vector DB): при ожидаемом масштабе (тысячи проектов, не
  миллионы) отдельный ANN-индекс избыточен, а `sqlite-vec` требует
  загрузки нативного расширения SQLite — лишняя точка отказа на этой
  конфигурации (venv под `hermes`, без root), в духе уже пойманных
  проблем с бриджингом конфига (`docker_volumes`, `TERMINAL_CWD`).
  Поиск — brute-force cosine similarity на Python (`numpy`), приемлемо
  для этого объёма данных.
- Файл БД — отдельный, не трогает внутренние SQLite Hermes
  (`~/.hermes/plugins/project-index/index.db` или аналог).

### Реализация — новый плагин (по образцу `content-injection-guard`)

Используем `ctx.register_tool(...)` — плагин может регистрировать
полноценные новые инструменты, не только хуки (см. `plugins.enabled`,
`~/.hermes/plugins/`). Два инструмента:

- **`project_index_update(project_path)`** — считает embedding из
  «Название + Краткое описание + tags» (см. ниже, что именно эмбеддить),
  сохраняет/обновляет строку в таблице (ключ — путь проекта; плюс
  `user`, `group`, `status`, `tags`, `updated_at`).
  Если запрос к wormsoft.ru упал (429/500) — не блокирует создание
  проекта, просто оставляет его непроиндексированным до следующего
  вызова.
- **`project_search_similar(query, top_k=5)`** — считает embedding
  запроса, cosine similarity по всем векторам **этого** пользователя
  (фильтр по `user`), возвращает top-k без жёсткого порога отсечения
  (человек сам решает по выдаче — компромисс с уже принятым решением
  «поиск только по явной просьбе», см. «Жизненный цикл сессии» выше).
  `archived`-проекты не исключаются из выдачи — если человек ищет
  что-то похожее, старый завершённый проект тоже может быть ответом,
  просто в результате виден `status`.
- Отдельно — `project_reindex_all()`: пересчитать индекс для всех
  `about.md` в пространстве пользователя. Нужен для бэкфилла (первый
  запуск на существующих проектах) и восстановления, если файл БД
  потерялся/повредился — обычный batch-скрипт, не критичный путь.
- Плюс `project_move(...)` — перенос проекта между `ALL`/группами,
  использует те же таблицу и `project_index_update` внутри себя, см.
  отдельный раздел «Перенос проекта» ниже.

### Что эмбеддить

Только **Название + Краткое описание + tags** из `about.md` — не
«Опорные точки»/«На чём остановились». Короче, дешевле, не «размывается»
по мере роста истории проекта (эти два поля вручную/агентом обновляются
не так часто, векторный поиск не должен требовать переиндексации каждый
раз, когда меняется прогресс внутри уже понятной темы).

### Когда пересчитывать

Сразу при создании/правке `about.md` — агент вызывает
`project_index_update` сразу после записи файла. Это должно стать
явным правилом в `AGENTS.md`-шаблоне проекта (или в `SOUL.md`, раз это
поведение общее для всех проектов). Индекс всегда актуален, стоимость
разумна — это один короткий embedding-запрос на изменение, не батч.
